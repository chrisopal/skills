# 投标 Skill 质量闭环与双原件回归

用户已确认采用第二种路径：保留17个核心Skill和宿主模型执行方式，增加共享检查脚本与宿主规程；使用东台和青草沙两份既有原件验证。不增加依赖、数据库、独立工作流服务或远端材料传输。

## 决策与边界

- 评分条件由宿主回读原文拆解，独立复审逐条记录正文及证据；脚本检查覆盖、引用、版本与客观约束，不认证语义、企业真实性或预测主观评分。
- 复用现有需求/评分/材料ID、章节提案、CAS和快照。质量计划保存在项目profiles，评审保存在reviews。来源变化必须重新复核，不用更新哈希冒充重新评审。
- 共同事实保存期望值与正文定位，检查工期、人员、金额及系统参数的一致性。明确否决和必需材料阻塞；纯失分形成整改或明确风险记录。
- 整改计划只派发受影响章节/图任务；宿主执行实际改写与生图，脚本不冒充模型。现有成功章节复用，执行中任务先核查真实宿主状态，失败限次。
- 篇幅根据直接/继承评分贡献、需求复杂度与文体分配；固定表及清单不按需求条数机械扩写。用户明确目标和原文强制规则优先。
- 导出检查绑定排版spec和实际DOCX/PDF哈希，验证正文、标题、表格及插图。视觉检查仍需实际渲染和逐页证据，不能将机器检查提升为业务通过。
- 统一预检记录实际可用的OCR、图工具、宿主生图/子Agent/知识库及导出字体；未探测和不具备明确分开。本地中文检索支持查询拆解，远端权限与版本仍由宿主核验。

替代方案：仅追加提示词成本低但无法稳定检查版本与漏项；独立调度服务提供更多自动化但改变可移植边界。共享文件契约与检查脚本复用现有分发机制，维护成本适中。

## 实施顺序与验收

1. 实现逐条条件、共同事实及实际成稿检查，并补回归；同步独立安装分发依赖。
2. 调整篇幅/中文检索，增加质量整改计划和能力预检；总控、写作、评审、导出Skill明确调用。
3. 从两个历史项目创建独立副本，核对原PDF哈希、分类、目录及评分/资格要求，保存新版执行记录。
4. 运行缺评分条件、缺必需材料、缺图、工期矛盾、漏章节/导出漂移等负向用例，再实际整改和复核；重新生成候选Word/PDF并读回和渲染。
