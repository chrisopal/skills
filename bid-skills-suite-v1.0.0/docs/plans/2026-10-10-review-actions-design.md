# 评审整改动作设计

## 需求与边界

用户要求评审未通过后能一键修复、重写或提升。沿用现有可移植 Skill、文件工作区和宿主 Agent，不增加模型 SDK、数据库、后台任务引擎或依赖。

- 修复：按本轮未通过项补齐正文机制、响应和已授权可用材料引用。
- 重写：重构选定章节，保留强制目录、事实约束、需求和评分对应。
- 提升：结合评分条件、知识依据、实施机制、异常处置及验收方法提高章节质量，不能只增加字数。
- 资质原件、签章、保证金、真实演示和招标歧义必须单列待补／待确认，生成文字不能把它们变为已满足。

选用“网页创建版本绑定任务 + 宿主 Skill 领取执行 + 当前版本重评”。全书重新生成会覆盖已合格章节；在本地网页中新增直接调用模型的服务则绕开宿主能力与可移植边界，均不采用。

## UI Blueprint

保留：章节目录、正文编辑、写作设置、来源依据与现有深浅色主题。
增加：正文上方一个紧凑的“评审整改”操作区，范围为“未通过项／当前章节”，三个动作按钮，当前任务状态和按需展开的交接指令。复用现有语义颜色与按钮；窄屏自然换行。

状态：未评审、评审过期、可创建任务、创建中、待宿主执行、宿主执行中、待补材料、修改后待重评、重评仍有缺项。未保存正文、请求重复和版本冲突都有明确反馈。没有自动唤醒宿主的接口时，明确显示“待宿主执行”，不得显示正在生成。

## 数据与执行

请求保存到 `work/review-actions/`，绑定项目、正文 revision/SHA、评审及输入 SHA、动作、范围、缺项与章节。请求 ID 保证重复点击幂等；领取前再次比较绑定，任何改变使旧请求失效。历史保留。

宿主按任务卡读原文、评分条件、知识与证据；局部修复或按章节重写；图任务交给 bid-visuals；沿用编辑器或 writing_batch 的保存／合并约束。执行记录必须包含实际调用与修改证据。完成写作后重新评审，旧评审与旧导出不能继续充当当前结论。最多两轮；仍未通过时展示原因和下一步。

结构检查通过、语义评审通过和正式投标条件满足分别记录。任务完成不能自动宣布正式交付通过。

## 验证

回归覆盖幂等、非法路径、过期输入、缺评审、材料缺口、无实际修改、无当前重评和轮次限制。复制东台、青草沙项目进行请求→领取→实际修改→重新评审回读；保留原测试工作区。真实浏览器检查操作、未保存保护、任务恢复，以及 1440/1920/390 深浅色布局。
