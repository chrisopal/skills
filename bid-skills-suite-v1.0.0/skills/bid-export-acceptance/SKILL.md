# 16｜导出与成稿验收

生成并核验实际Word／PDF交付文件，确保成稿对应已审核版本且没有漏页、乱码或内部信息泄漏。

运行条件：需支持读取项目文件；可选脚本需要 Python 3.10+，文档、视觉/OCR 与绘图能力由宿主提供。

## 触发与边界

当用户提出“导出标书、Word/PDF成稿、交付打包、检查目录页码、实际文件验收。”时使用。不代签盖章、加密递交或上传交易平台；文件生成成功不等于业务验收通过。

## 开始前

先读 [共同证据与安全约定](references/evidence-and-safety.md)。仅当需要细化操作时读 [专项操作手册](references/playbook.md)；输出字段与示例参见 [产物契约](references/output-contract.md)。

输入：当前14文档工作稿、有效15评审、原始格式要求、用户交付授权及指定输出格式。

上游技能：`bid-document-layout, bid-review-remediation`。独立使用时接收用户提供的等价文件，记录实际输入，不要求虚构完整流程状态。检查原件和产物版本；缺关键信息时给出范围受限的草稿及缺口。

完整候选编标及宿主对话修订的保存、失效和重导出规则见[写作流程](references/WRITING_WORKFLOW.md)。

## 执行步骤

1. **步骤1**

   重新计算15所绑定输入文件的真实哈希；任何变化先返回15复核，不用“只是排版”跳过验证。

   `last-review` hash不匹配时禁止ready。完整编标可导出明确标注阻塞的`draft_only`候选，但eligible/正式交付门禁和人工授权不变；复杂固定表、真实TOC/页码及逐页QA未由宿主工具完成时不得标passed。

2. **步骤2**

   检查未采纳草稿、缺证据、缺图、未签署、未更新目录域和未解决阻塞；只允许明确标识的内部草稿绕开正式交付门禁。

3. **步骤3**

   使用宿主文档工具或包内受控脚本生成文件；Word和PDF分别记录生成工具、版本与输入摘要，缺依赖时明确失败不伪造扩展名。

4. **步骤4**

   检查实际文件能否打开，提取文本并比对标题、关键数字、固定声明和附件；内部R-ID／模型提示／待确认标签不得泄漏。

5. **步骤5**

   渲染并逐页核对页眉页脚、目录跳转、分页、长表、图片和插页。核对“页”等字符的实际编码，不能用自定义替换掩盖错误。

6. **步骤6**

   暗标按06检查显性与元数据身份；文件名、修订记录、批注、隐藏内容和外链也进入检查，不自动删改合法证据。

7. **步骤7**

   导出完成后再次核对评审输入未变，并生成文件名、SHA256、字节数、格式、检查状态与待办的清单；缺实际核验不得标passed。

8. **步骤8**

   仅打包用户允许交付的文件，内部证据与决策台账默认另存。提供文件路径和交付结论，不自动向外部发送或提交。

## 产物与交接

保存 `16-delivery-manifest.json`（机器可读）和同名 `.md`（可读报告），使用 [JSON模板](assets/output.template.json) 与 [报告模板](assets/report.template.md)。字段必须符合 [JSON Schema](assets/output.schema.json)。不要把模板空值直接当结果；详细演示见 [合成示例](assets/example.output.json)。

01—14产物放项目`artifacts/`，15放`reviews/`，16放`deliverables/`，17放`work/`。来源原件只读置于`inputs/`；图表置于`assets/`；规则配置置于`profiles/`。路径始终相对用户指定项目根，不写死本技能安装目录。

每个输出记录`project_id / artifact_id / revision / inputs / status`。`inputs`内SHA256从实际输入文件计算。缺依赖、未运行检查和待确认分别保留；不把模型产生结果等同于业务完成。

可选执行本技能目录内的校验器：

```bash
python scripts/validate_output.py /absolute/path/to/16-delivery-manifest.json
```

脚本只校验结构及部分一致性，不检查所有真实语义与授权。依赖不足可按清单人工检查，但必须写明“脚本未运行”。

## 验收检查

- [ ] 导出前后评审输入身份一致。
- [ ] 实际文件经过文本和视觉检查。
- [ ] 没有内部标记、缺图或静默漏附件。
- [ ] 签署／授权状态明确。
- [ ] 交付包不混入内部敏感资料。

## 人工确认点

逐页视觉与文本核验、签署待办及对外发布由真实用户确认；没有授权只产内部草稿。

## 常见陷阱

- 有PDF扩展名不等于有效PDF。
- 看起来相同的汉字可能有错误Unicode映射。
- 导出成功不代表Word目录域已正确刷新。
- 文件哈希能验完整性，不能证明法律效力或真实性。

## 调用示例

> 请先核验当前评审是否过期，再导出指定格式，检查实际文件的内容、页码、表格、附件和内部标记，生成交付清单。

示例原件 `assets/synthetic-tender.md` 和 `assets/synthetic-supplier.md` 全为合成资料，不能用作真实投标证据。场景配置参考 `assets/profile-catalog.json`，所有条目只是待项目核验的种子，不是已通过业务验收的行业规则。

## 失败与恢复

先保存已完成的产物、失败范围和下一步；原件变更或输入哈希变化时重核受影响内容。不要自动覆盖人工新版本，不代签批，不上传资料，不声称已在后台继续运行。测试建议见 `tests/cases.json`；这些是待执行的业务评测用例，不是已通过记录。
