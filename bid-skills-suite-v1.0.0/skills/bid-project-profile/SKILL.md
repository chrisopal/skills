# 02｜项目画像与场景适配

建立所有后续技能共同使用的项目上下文，并选择明确版本的场景配置。

运行条件：需支持读取项目文件；可选脚本需要 Python 3.10+，文档、视觉/OCR 与绘图能力由宿主提供。

## 触发与边界

当用户提出“识别采购类型、项目画像、政府或企业采购场景、行业适配、选择领域包。”时使用。不因采购人名称直接判定法律适用，不推定缺失预算、保证金、工期或招采制度。

## 开始前

先读 [共同证据与安全约定](references/evidence-and-safety.md)。仅当需要细化操作时读 [专项操作手册](references/playbook.md)；输出字段与示例参见 [产物契约](references/output-contract.md)。

输入：01来源清单与原文；用户确认的投标主体、项目目标、参与标包；可用规则包和领域包。

上游技能：`bid-source-intake`。独立使用时接收用户提供的等价文件，记录实际输入，不要求虚构完整流程状态。检查原件和产物版本；缺关键信息时给出范围受限的草稿及缺口。

## 首次分类与模板

首次识别按 [分类与模板路由](references/TENDER_ROUTING.md) 运行 scripts/tender_router.py brief，宿主按原文提出分类后运行 route。采用工程施工、硬件供货、软件开发与系统集成、服务与外包四类；智慧化为场景标签和组合入口。分别确认标包数量与每包单类／组合，保存02-tender-routing.json，记录其实际版本和SHA256到本产物inputs。无证据时保留unknown。

判单包前交叉核对公告、前附表、采购清单和报价表，不能只读总项目摘要。可分开报价或分别中标但未明确标包时保留歧义。软件按实际许可、报价行、数量与对接范围判断，既不把固件自动当集成，也不漏掉随设备采购的独立软件。

## 执行步骤

1. **步骤1**

   确认用户位于投标人侧，并确认本次是完整编标、理解分析、修订还是独立评审；不要混入招标人编制文件或组织评标任务。

2. **步骤2**

   从明确原文提取项目名称、采购人、采购对象、地点、范围、标包、预算、时间、交付与验收条件；没有证据的字段使用null和待确认说明。

3. **步骤3**

   将配置拆成招采规则、行业领域、文档模板、企业素材四层。工程、设备、软件集成、服务可组合；政府／企业不是行业分类。

4. **步骤4**

   为推荐的配置列出证据、版本与适用理由。无领域包时使用通用框架并声明专业规则缺口，不强行套最相似行业。

5. **处理时间**

   保留原文和明确时区，日期未说明年份或时区时不能自行补齐。不同附件的截止日期冲突进入待澄清项。

6. **步骤6**

   已核验的适用法律规则与招标条款冲突时标记待专业判断，不机械设置“招标文件覆盖法律”；离线环境不宣称法规已最新核验。

7. **步骤7**

   建立统一术语、项目简称、投标主体、币种、计量单位、能力边界和禁止承诺项，后续技能使用同一上下文版本。

8. **步骤8**

   输出配置选择与用户确认点。配置种子只提供检查维度，不能自动变成项目要求或企业能力；经确认后冻结本轮上下文摘要。

## 产物与交接

保存 `02-project-profile.json`（机器可读）和同名 `.md`（可读报告），使用 [JSON模板](assets/output.template.json) 与 [报告模板](assets/report.template.md)。字段必须符合 [JSON Schema](assets/output.schema.json)。不要把模板空值直接当结果；详细演示见 [合成示例](assets/example.output.json)。

01—14产物放项目`artifacts/`，15放`reviews/`，16放`deliverables/`，17放`work/`。来源原件只读置于`inputs/`；图表置于`assets/`；规则配置置于`profiles/`。路径始终相对用户指定项目根，不写死本技能安装目录。

每个输出记录`project_id / artifact_id / revision / inputs / status`。`inputs`内SHA256从实际输入文件计算。缺依赖、未运行检查和待确认分别保留；不把模型产生结果等同于业务完成。

可选执行本技能目录内的校验器：

```bash
python scripts/validate_output.py /absolute/path/to/02-project-profile.json
```

脚本只校验结构及部分一致性，不检查所有真实语义与授权。依赖不足可按清单人工检查，但必须写明“脚本未运行”。

## 验收检查

- [ ] 采购方式与行业领域分开。
- [ ] 关键字段有来源或明确未知。
- [ ] 规则包和领域包版本被记录。
- [ ] 没有将候选配置当作认证通过。
- [ ] 没有使用非授权企业资料。

## 人工确认点

投标主体、参与标包、适用规则、核心项目边界及外部服务传输范围需真实授权确认。类型识别先保存候选与模板依据：明确范围可继续03—06候选提取，重大分类/组合歧义或用户要求先确认时再请用户决定；正式采纳前落实理解确认。记录绑定实际路由版本，详见[分类确认时点](references/TENDER_ROUTING.md)。

## 常见陷阱

- 国有企业身份不足以自动确定具体采购制度。
- “标准模板”不能覆盖客户指定表格。
- 某行业常见功能不能自动加入客户需求。
- 项目简称相近不等于同一标包。

## 调用示例

> 基于已整理的来源，生成项目上下文卡，区分招采规则与行业领域，推荐配置并列出尚需我确认的事项。

示例原件 `assets/synthetic-tender.md` 和 `assets/synthetic-supplier.md` 全为合成资料，不能用作真实投标证据。场景配置参考 `assets/profile-catalog.json`，所有条目只是待项目核验的种子，不是已通过业务验收的行业规则。

## 失败与恢复

先保存已完成的产物、失败范围和下一步；原件变更或输入哈希变化时重核受影响内容。不要自动覆盖人工新版本，不代签批，不上传资料，不声称已在后台继续运行。测试建议见 `tests/cases.json`；这些是待执行的业务评测用例，不是已通过记录。
