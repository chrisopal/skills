# 首次识别、分类模板与组合项目

## 分类方式

| 基础类别 | 使用模板 | 判断对象 | 不构成该类别的单独证据 |
|---|---|---|---|
| 工程施工 | construction | 土建、装修、管线、机电施工等实际承包工作 | 硬件附带上架、软件名称中的“工程” |
| 硬件供货 | hardware_supply | 本次交付的设备、数量、规格和货物清单 | 现有运行环境、建议配置、投标人历史设备案例 |
| 软件开发与系统集成 | software_integration | 软件许可、开发、平台、接口、数据迁移和集成实施 | 设备固件、仅说明设备兼容某软件 |
| 服务与外包 | service_outsourcing | 独立采购的运维、驻场、业务外包、咨询等持续或专业服务 | 随产品附带的常规安装、培训和质保 |

智慧化综合项目是组合入口，不是第五个互斥类别。smart_factory、smart_park、smart_campus 等是场景标签。项目标题可作为初筛线索，正式候选分类必须回到采购范围、标的清单和交付责任。政府／企业采购配置及采购文件声明的货物／服务类型，独立于上述业务分类。

先识别标包，再识别每包工作内容。一包采购软件和硬件是组合；两包分别采购软件和硬件是两个单类包。一个项目可能有多个组合包。不要按类别自动拆分法律意义上的标包，也不要把几份附件自动当成几个包。

判定单包前，必须交叉核对公告、投标人须知前附表、采购清单和报价表中的包件／标段／合同数量、各包编号及兼投兼中规则。总项目的一行概述不能覆盖明确的子包清单。两张报价表或允许一个／两个中标人，不必然等于两个固定标包；来源无法确定时将 lot_structure 设为 unknown，列明候选部分及待澄清问题。

软件边界同时检查技术要求和报价清单。设备嵌入功能通常不单列组件，但单独的软件许可、套数、报价行及平台数据对接可构成软件采购；不能把所有随设备采购的软件都排除。对照原表图像核对单元格，避免把跨页软件名称读成上一个设备的附属功能。

## 工具与宿主分工

宿主模型负责理解原文和提出分类。tender_router.py 负责验证原件身份、引用和分类结构，并匹配已版本化的提取模板；脚本不调用模型，也不使用关键词打分替代语义判断。

首次执行先做 01 全来源登记与解析，再生成分类材料。初步分类不能裁掉其他章节。原文、配置和输出均在用户项目目录中保存。

~~~bash
python scripts/tender_router.py brief \
  --project /absolute/project \
  --intake artifacts/01-source-intake.json \
  --out work/routing-brief.json
~~~

宿主读取 brief 和所有相关原文，按其中的 decision schema 保存 work/classification.json。每个组件提供类别、判断理由及真实 source_id/location/quote；标包结构需来源依据。信息不足时保留 unknown，不得填造标包、类别或作用范围。

决定必须携带 brief 的 catalog_sha256 与 intake_sha256；目录定义或原文变化须重读后生成新决定。每个 scenario_tag 都提供对应 scenario_evidence（tag、rationale、evidence）；没有场景标签时两数组均为空。脚本将来源角色、路径、版本、字节和哈希与 source-registry.json 核对，供应商材料不能变成招标范围依据。

~~~bash
python scripts/tender_router.py route \
  --project /absolute/project \
  --intake artifacts/01-source-intake.json \
  --decision work/classification.json \
  --out artifacts/02-tender-routing.json
~~~

输出冻结模板版本和内容，包含通用轨道与各标包所需类别模板；状态为候选待核验。原件或 01 变化后重新生成 brief 和分类，使用新产物路径保存，不覆盖旧版本。禁止把先前项目的分类或模板结论复制到本项目。命令失败时修正缺口，不能手工删掉阻塞标记冒充通过。

## 分类何时需要用户确认

先识别类别、标包和组合，再匹配提取模板。给用户展示候选类别、判断依据、选中模板版本及未确定范围；不能将路由脚本成功视为用户已确认。

- 原文范围清楚、没有用户指定“先确认再分析”的要求时，可按候选模板继续03—06理解提取，保持needs_review；无需每一个明确单类项目都打断用户。
- 类别/单包或组合包有歧义、资料缺失会改变提取范围、涉及哪个包参与或适用采购规则时，提出具体选择让真实用户决定。在决定前仍可读原件和提取公共内容，不擅自选定有争议的范围。
- 完成understand后，进入以选定标包、主体和规则为依据的响应策划、方案、承诺前，落实G1理解确认。用户明确指定的范围可作为相应范围依据，不能扩大成其他批准。
- 用户要求每次先确认类别时，遵从该顺序。更换原件或用户调整分类/标包时生成新路由，将受影响下游标stale并重核。

确认可保存到`confirmations/classification.json`，参照模板`assets/tender-routing/classification-confirmation.template.json`（独立安装位于技能assets下）。记录project_id、实际路由artifact_id/revision/path/hash、参与标包、决定及真实用户消息/宿主授权引用。AI只填候选与pending，不能替用户把decision改成approved。该记录仅承载证据，离线文件不能认证批准人；无真实授权时保持候选状态。

## 四条提取轨道

1. **项目基础信息**：项目名称、编号、采购人、采购方式原文、标包、预算／限价、截止时间、履约地点、周期与交付范围。预算、限价、报价和评分金额不得混为一项。
2. **采购需求**：主体、对象、能力、数量、参数、单位、条件、交付、服务和验收；保留 AND／OR、否定、区间与标包边界。公共条款与类别专属条款都读取。
3. **评分**：计分叶子、汇总节点、分值、权重、档次、封顶、互斥、证明材料与评分对象；价格分公式保留原文，未选用的模板选项不计入本项目总分。
4. **资格与否决**：资格条件、实质响应、明确否决、提交要求与履约风险分开；只有原文明示后果才能登记为明确否决。招标失败条件、投标无效与中标后违约也分别记录。

四类模板是提取检查框架，不是成稿目录模板。客户强制目录和固定表格仍由 06 单独提取并优先遵守。类别清单不限制发现其他要求。

02—06 将路由产物的实际路径、版本和 SHA256 加入各自 inputs。使用本包已有的输出 Schema 交接结果，不另造一套正式需求权威。每条事实仍引用原件，不能只引用分类计划或行业知识。

## 版式和覆盖

每份来源保留章节、页码或段落／单元格定位。表格先确认表头、列角色、合并单元格和续表，再按行提取；阅读顺序错乱时回看原图，不从线性文本猜列对应。基础 PDF 文字提取和 OCR 都不保证表格语义完整。

正文、附件、合同、评分表和补遗分别覆盖。记录已处理页／表、未提供附件、密码／损坏／乱码／扫描页。资料缺失只允许限定范围草稿。通用范本中未选择的复选项、说明文字和历史业绩示例不能成为本项目采购事实。

全量运行须逐项核对基础信息字段，并为四条轨道记录已读章节／页／表和未处理范围；不能抽取每轨两条就报告该轨完成。只读定向片段时明确标为 targeted_non_exhaustive。先查证据再修改判断：预测与标注不同，双方都回看原页，保留标注修订记录，不强迫模型迎合错误答案。

## 回归方式

benchmarks/public-tenders 保存公开文件来源和候选标注；原始 PDF 保存在独立本地语料目录。benchmark_tenders.py audit 对原件哈希、页码和标注引用逐条回查。evaluate 比较独立结果的分类和已标注证据锚点，未标注内容不计成误报。

标注范围、模型版本、输入范围和结果分开记录。锚点覆盖不是全文召回率；引用正确不证明解释正确。经过 AI 核对的标注须保留未行业专家审定状态。不同宿主／模型更换后重跑，不能把某次 Codex 结果推广为所有宿主通过。
