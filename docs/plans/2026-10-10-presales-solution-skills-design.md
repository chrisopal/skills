# 通用 B 端售前方案：流程与技能设计

日期：2026-10-10

状态：设计提案，待业务讨论；已完成一条模拟流程演练，新售前 Skill 尚未实现或安装。

已确认定位：通用 B 端售前，允许按行业补充材料。

本轮范围：定义工作流程、各环节职责、交接产物、确认节点、PPT 接口和方案审核。实际客户方案与技能开发不在原设计轮范围。2026-10-11 按用户要求追加模拟测试，PPT 使用本地 `ppt-master-plus`，见[验证记录](2026-10-11-presales-ppt-master-plus-validation.md)。

## 1. 目标与边界

把 Word、PDF、会议记录、现场照片、客户邮件或补充说明，转成有来源、有范围、有产品及交付依据的客户方案，再交给现有 PPT Skill 制作。最终验收既检查方案是否回应客户问题，也检查实际 PPT 是否忠实表达方案。

售前的中心问题是：**客户为什么要做、需要解决什么、我们如何解决、依据是什么、如何落地、希望客户下一步决定什么。** 输入可以不完整，结果允许是交流版、建议版或评审版，不假定每次都达到合同或实施设计深度。

- 售前负责需求理解、方案建议、能力匹配、汇报设计与方案质量；不自动扩展到线索运营、销售预测、合同签署或项目管理。
- 投标有明确评分和提交规则时交接投标套件；不把售前需求自动解释为废标条件。
- 需要完整企业诊断、目标运营模式或深度架构规划时，调用咨询能力；不强制每份售前建议书完成全套咨询或 4A 模型。
- PPT Skill 负责视觉呈现和文件制作，不能替上游决定产品能力、交付范围和收益承诺。
- 行业包提供术语、常见问题、检查维度和候选素材，不自动生成“客户已确认需求”。

## 2. 组织方式选择

| 方式 | 适用与代价 |
|---|---|
| 一个大型售前 Skill | 启动简单，但独立评审、局部重跑、版本追踪和内容复用容易混在一起。 |
| **一个总控 + 九个业务 Skill + 外部 PPT Skill（建议）** | 按可独立交付的业务结果划分，既能串起全流程，也能只做需求、脑图或评审。 |
| 全面复用投标／咨询套件 | 可用于深度专项任务；若直接作为售前默认流程，容易带入评分、资格、全套架构等不适用门槛。 |

这里的数量来自职责划分，不代表每次需要十次独立模型调用，也不要求另建工作流平台。小项目可以在一次工作中完成多个环节，只需保留关键交接结果。首版用项目文件和总控说明即可，不新建服务、数据库或专用 PPT 引擎。

## 3. 从输入到交付的主流程

1. **建立任务简报**：确认客户、会议受众、沟通阶段、汇报目的、预期决策、时间及交付形式。
2. **归集并读取材料**：登记 Word/PDF/会议记录/图片等，保存来源定位和未读范围。
3. **梳理客户需求**：形成目标、现状、痛点、场景、约束、优先级及待核实理解。
4. **形成汇报脑图初稿**：组织“为什么做—做什么—怎么做—凭什么—如何推进—请客户决定什么”，暴露逻辑与材料缺口。
5. **澄清并补充输入**：按影响排序提问，回写需求和脑图；范围清楚的分支可以继续准备。
6. **选择材料并设计方案**：读取产品／公司／案例材料，核实能力组合与差距，形成方案边界、路径、实施前提和价值说明；必要时调整脑图。
7. **确认需求理解与汇报方向**：集中审阅需求摘要、脑图、关键方案选择及尚未解决的问题，记录确认范围。
8. **编制逐页大纲并确认**：确定章节、每页作用、核心结论、证据、图表、页数及讲述顺序。
9. **编写完整逐页内容包**：把材料转成客户化正文、图表规格和讲稿；先通过内容审核，再交给 PPT Skill。
10. **制作并验收实际 PPT**：PPT Skill 制作；售前审核 Skill 检查实际文件、渲染页面、需求覆盖和承诺一致性；整改后复核。
11. **交付与反馈回流**：在已有授权范围内交付，记录交付版本；新反馈回到相应需求、方案或页面，复用仍有效的成果。

这是一条带回路的主线。澄清贯穿全过程；材料检索在需求初步形成后即可开始，并在逐页写作时再次精确选材。第 7 步可以按会议节奏分两次讨论，也可合并；不需要每个内部文件都单独确认。

### 三个需要业务确认的结果

| 节点 | 提供给人的可审阅结果 | 确认的含义 |
|---|---|---|
| A：理解和方向 | 需求摘要、汇报脑图、方案方向、关键差距、澄清项 | 范围与讲述方向可作为下一阶段依据；内部确认不冒充客户确认。 |
| B：逐页大纲 | 每页标题、结论、内容范围、证据和图表计划 | 可以按这个版本开展详细内容与制作。 |
| C：交付版本 | 实际 PPT、可用预览、当前审核报告、剩余事项 | 由有权人员确认具体版本及使用范围；审核通过不自动授权外发。 |

用户已有明确确认或授权时沿用，不重复询问；大纲确认同时明确授权后续制作时，非实质性的文字压缩和排版无需反复确认。新增关键范围、产品承诺、价格／工期或重大结论时，只确认变化部分。授权不明时仍可完成清楚标注的候选稿。

## 4. 每个 Skill 的设计

以下名称是拟定标识，不代表技能已安装。每个业务 Skill 都能接收用户提供的等价文件独立运行，不要求补造完整流程历史。

### 00｜presales-orchestrator：售前方案总控

- **触发**：做一份售前方案、继续现有方案、按客户反馈修订、安排整个流程。
- **输入**：任务目标、项目目录、已有材料及成果、已确认决定、可用工具与 Skill。
- **处理**：建立简报；识别本次模式与停止位置；按依赖调用业务技能；汇总澄清问题；记录版本、确认和下游影响。总控不另写一套专业结论。
- **输出**：`project-brief`、`artifact-register`、`workflow-state`、`decision-log`。
- **完成条件**：下一步与责任明确，每个已完成成果可回读，实际状态与用户要求一致。
- **异常**：缺少 OCR、PPT 或资料检索能力时记录影响，交付可完成部分；不虚报后台运行或交付。
- **模式**：`full` 全流程、`discovery` 到需求／脑图、`outline` 到逐页大纲、`review` 独立审核、`revise` 变更续作。输出深度按交流／建议／评审目的调整。

### 01｜presales-source-intake：客户材料归集与证据整理

- **触发**：整理客户资料、读取会议记录／附件／照片、补充新资料。
- **输入**：原始文件、链接或用户陈述；材料提供者、日期、适用客户等已知信息。
- **处理**：原件只读登记；优先原生解析，扫描页及图片做 OCR 和视觉理解；核对跨页表格、附件引用、说话人和时间；保留原文与整理内容的映射。
- **输出**：`source-register`、`evidence-register`、`reading-coverage`，必要的原文摘录及图片区域定位。
- **完成条件**：每份材料都有已读／部分已读／失败记录；重要摘录能定位到文件版本及页码、段落、时间或图片区域。
- **异常**：不可辨文字不补写；缺失附件和被裁切页面保留缺口。现场照片只能证明可见内容，不能据此断言设备联网、系统兼容或产能。

### 02｜presales-requirements：需求理解与结构化

- **触发**：梳理客户需求、整理痛点、把交流内容变成需求清单。
- **输入**：项目简报、来源及证据记录。
- **处理**：分开目标、现状、痛点、业务场景、功能／非功能需求、约束和成功标准；保留原文条件、单位及范围；归并重复，保留冲突及不同角色意见。
- **输出**：`requirements`、`stakeholder-concerns`、`requirement-summary`、供澄清 Skill 使用的缺口。
- **完成条件**：客户明确诉求、分析推断、我方建议和未知项分开；重要需求有来源、业务影响及可讨论的成功标准。
- **异常**：客户未排优先级时标“建议优先级”；不能把销售个人判断写成客户全体确认，也不能以常见行业需求填补客户事实。

### 03｜presales-clarification：澄清与补充输入

- **触发**：列出要问客户的问题、准备下一次访谈、处理材料冲突、回写客户回答。
- **输入**：需求、脑图、能力差距、当前阶段及缺失证据。
- **处理**：每个问题说明为什么问、谁适合回答、需要何种材料、不回答会影响哪里；按阻塞方案选择、影响可信度、一般补充分级；合并同一对象的重复问题。
- **输出**：`clarification-log`、客户沟通提纲、补充资料清单、带来源的回答和影响记录。
- **完成条件**：问题可回答、责任可定位；关闭问题需要实际回答或证据。假设推进与事实澄清不能混为一谈。
- **异常**：无人答复时可在显式假设下制作讨论稿；影响关键承诺的未知项保留阻塞。只准备问题，不默认发送客户或群聊。

### 04｜presales-storyline：汇报逻辑与脑图

- **触发**：先出一个方案脑图、整理汇报逻辑、换一种面向管理层的讲法。
- **输入**：需求摘要、受众与决策目标、已知方案方向、澄清状态。
- **处理**：组织论点和论据，说明每一分支回答什么客户问题、帮助形成什么判断；区分已支持内容、待补材料和待澄清分支。脑图先于页码，不过早锁死页数。
- **输出**：可编辑的层级脑图源 `storyline-map`、汇报摘要、缺口标记；可按需要调用绘图能力呈现。
- **完成条件**：各分支能说明客户关联和叙事作用；公司介绍与产品介绍只在支持结论时出现；最终有清楚的下一步决策请求。
- **异常**：受众／目的未知时给出明确标注的假设；新增信息改变主结论时更新脑图及受影响确认。

### 05｜presales-material-matching：产品、公司与案例材料匹配

- **触发**：用现有公司／产品资料组合方案、寻找案例和能力证明、补充某一页的素材。
- **输入**：需求或页面任务、可用资料库、本项目已授权材料、适用行业／产品／版本信息。
- **处理**：先检查适用性再判断相关性；核对产品版本、标准能力／配置／定制／路线图、公司主体、案例真实性与使用范围；截取内容时保留来源定位。
- **输出**：`material-selection`、`capability-matrix`、材料缺口及候选图表／截图。候选、已核实适用、不可使用分开。
- **完成条件**：每项关键能力和案例有证据；适用边界可读；旧 PPT 的营销描述不直接升级为交付事实。
- **异常**：矛盾材料并列并交澄清，不按最新上传覆盖。外部或跨客户案例无法确认使用范围时，仅保留内部候选，不流入客户成稿。
- **组合规则**：基础公司包 + 产品包 + 行业包 + 场景包 + 项目专用材料可以组合；项目已确认约束决定适用性，版本冲突必须核实。模板只提供视觉形式，不提供客户事实。

### 06｜presales-solution-design：售前方案设计与能力组合

- **触发**：把需求变成解决方案、组合产品能力、比较方案选项、明确交付边界。
- **输入**：需求、脑图、澄清回答、能力矩阵、约束和实施前提。
- **处理**：建立“需求—响应机制—产品／服务能力—证据—交付前提—验证方式”映射；定义范围内外、关键场景、系统边界与集成、适当深度的架构、实施阶段和客户配合条件。
- **输出**：`solution-blueprint`、`requirement-response-matrix`、方案选项及取舍、实施／价值说明、待决事项。
- **完成条件**：重点需求有具体应对；标准、配置、定制、第三方依赖、暂不支持分开；方案描述能被产品或交付人员核验。
- **异常**：预算、收益、性能、周期没有依据时保留估算条件或未知；不为补齐页面编造数值。深度咨询或实施设计需求按范围转交既有专业能力。
- **深度**：简单产品交流可只需要场景与能力映射；复杂集成才增加架构、数据及安全等专项内容，不固定堆砌技术章节。

### 07｜presales-outline-planning：章节与逐页大纲

- **触发**：编制方案大纲、确认每页讲什么、压缩或扩展汇报时长。
- **输入**：当前有效的脑图和方案设计、受众、时长／页数要求、重点需求及可用素材。
- **处理**：把论点分配到章节和页面；确定每页目的、主结论、关键内容、依据及视觉意图；检查重点需求覆盖、重复页面和讲述节奏。
- **输出**：`page-outline`、需求到页面映射、附录安排、待确认页面列表。
- **完成条件**：逐页可审阅，重点需求有落点；每页不只是“背景／方案／价值”占位标题，而有清楚的内容计划。
- **异常**：页数不够时说明合并或转附录的取舍，不静默删去重要需求、限制条件和下一步事项。

### 08｜presales-content-authoring：逐页正文与 PPT 内容交接

- **触发**：按确认大纲写完整方案、准备 PPT Skill 输入、修改某页内容。
- **输入**：有效逐页大纲、方案蓝图、选定材料、语言及表达要求。
- **处理**：编写结论标题、正文、讲稿、数据表、图表规格、图源引用和客户可见的限定条件；做客户化解释，统一产品名称、数字口径与阶段范围。
- **输出**：`slide-content-pack`、图表规格、素材引用、引用索引及待解决项。
- **完成条件**：内容足以直接排版，PPT Skill 不需要猜业务结论或填事实；受限假设在对应页面可见，不能仅藏在讲稿或内部台账。
- **异常**：发现方案缺口回到 06，材料缺口回到 05，范围疑问回到 03；不能借润色悄悄扩大承诺。

### 09｜presales-solution-review：方案验收审核与整改复核

- **触发**：审核售前方案、检查是否回应需求、检查 PPT 能否交付、按审核意见整改。
- **输入**：审核对象及版本、用户要求、实际来源材料、需求与方案依据；最终验收另需实际 PPTX/PDF 或可回读的页面。
- **处理**：按当前阶段检查，不提前要求后续产物；独立回查关键来源；逐项检查覆盖、事实、可行性、逻辑和呈现；输出可定位的整改项，读取整改后版本再复核。
- **输出**：`review-report`、`findings`、逐项需求覆盖表、整改结果、当前版本使用建议。
- **完成条件**：每个结论有依据和对象定位；未知／未检查显式保留；重要问题关闭有新证据。详见第 8 节。
- **异常**：只有成稿、缺客户输入时，可审叙事、文件和内部一致性，但“满足客户需求”保持未核验。自检可帮助改稿，不能冒充独立评审或业务批准。

## 5. 脑图、逐页大纲与内容包的区别

| 产物 | 回答的问题 | 最小内容 |
|---|---|---|
| 汇报脑图 | 要讲清哪些问题、论点如何衔接？ | 节点 ID、父节点、客户问题、拟表达结论、关联需求、证据／缺口、待决问题。 |
| 逐页大纲 | 每个章节和每一页具体做什么？ | 页面 ID、章节、页面目的、主结论、拟写内容、对应需求、拟用材料、视觉意图、讲述时长。 |
| 逐页内容包 | 这页最终写什么、图里是什么？ | 实际标题与正文、图表数据／关系、图源、讲稿、限定条件、来源引用、审核状态。 |

示例脑图框架可从以下分支开始，按客户会议调整，不作为每次固定目录：

- 本次建议及希望确认的下一步。
- 客户目标、业务问题与当前限制。
- 优先解决的场景及成功标准。
- 推荐方案、能力组合与选择理由。
- 产品及案例依据、适用条件和差距。
- 实施路径、分工、价值验证与风险。

**示例，仅为演示，不代表真实客户事实：**客户说“希望减少跨部门重复录入”。需求记录保留这句话及会议定位；脑图设“减少重复录入的路径”；方案检查主数据归属、现有接口与权限；大纲安排“通过统一数据来源减少重复录入”页；内容包说明数据流和实施前提。若缺现状耗时基线，不能写“效率提升 30%”，可以列出试点测量方法。对应未决接口问题需要在方案与页面上保留条件。

## 6. 项目资料与交接约定

### 6.1 最小工作目录（拟定）

```text
<project>/
  inputs/        客户原件及本项目使用的资料快照
  work/          简报、状态、决定、澄清记录、产物索引
  artifacts/     需求、脑图、选材、方案、大纲、逐页内容包
  assets/        实际使用的图片、图表源及说明
  reviews/       阶段审核、问题单及复核记录
  deliverables/  当前交付文件及交付清单
```

第一版宜采用“一份结构化数据 + 按需生成的 Markdown／表格审阅视图”，不手工维护两个事实版本。原始文件无需重复复制到每个环节。文件放用户指定项目目录，不能写进已安装 Skill 的源码目录。

### 6.2 所有交接共有的信息

每个成果带 `project_id / artifact_id / revision / inputs / status`。`inputs` 记录来源版本和实际哈希；引用跨项目时必须明确来源及使用依据，不仅比较相同内容。正文使用稳定 ID，例如 SRC、EV、REQ、Q、MAT、SOL、SLIDE、FIND；修改保留原 ID，拆分／合并留下映射。

不把以下几类状态混成一个“已完成”：

- 产物状态：`draft / ready / stale / blocked`，其中 ready 仅表示可供下游使用。
- 证据类型：`customer-statement / observed / inferred / proposed / unknown`；客户陈述仍不自动等于经过验证的客观事实。
- 确认状态：`unconfirmed / confirmed / superseded`，确认记录对象、版本、实际确认人、身份、时间和范围。
- 审核结论：`pass / conditional / fail / not_checked`，明确适用阶段和未核验范围。

### 6.3 四类关键记录

| 记录 | 除共有信息外的最小字段 |
|---|---|
| 需求 | 原文与来源、客户角色、目标／场景、条件、约束、优先级及其依据、成功标准、证据类型、冲突及澄清引用。 |
| 澄清问题 | 问题、为什么问、影响对象、优先级、适合回答的人、所需材料、回答来源、处理决定及状态。 |
| 材料及能力匹配 | 来源位置、产品／公司主体、版本、适用条件、能力类别、需求／页面引用、可用范围、匹配结果及理由。 |
| 审核问题 | 严重度、检查标准、来源依据、实际对象／页码、发现、影响、整改责任角色、动作、复核证据及状态。 |

### 6.4 修改和恢复

新增资料先登记，再判断影响的需求、方案和页面；只有受影响成果和审核标 stale，不重做整个项目。替换原文件、PPT 手改、材料过期或产品版本变化都要重新核对。无关页面可以复用，但整份交付建议必须绑定最终完整文件版本。

首版默认顺序生成、集中合并。未来若按页并行写作，使用同一基准版本、独立草稿和单一合并者；没有真实并发执行记录时不宣称支持已验证的并行闭环。

## 7. 与现有 PPT Skill 的接口

沿用咨询套件“Slide Content Pack 表达讲什么、PPT Skill 决定如何呈现”的职责边界。先沿用现有字段，再加售前需要的需求、方案、材料及限定条件引用；本设计尚未实现适配器，不能声称任意 PPT Skill 已原生接收同一 JSON。

### 7.1 交给 PPT Skill 的内容

- 汇报信息：`deck_id / version / purpose / audience / decisions_required / language / page_budget / theme_profile / output_formats`。
- 叙事信息：`story_arc`、章节与页面顺序、正文与附录边界。
- 每页内容：`slide_id / section / title / key_message / supporting_points / speaker_notes`。
- 依据引用：`artifact_ids / evidence_ids`，售前扩展 `requirement_ids / solution_ids / material_ids`。
- 视觉输入：`visual_type / chart_spec / diagram_spec / layout_hint`、实际素材路径及图源。
- 约束：页面上的 `visible_caveats`、不可改动的数字／术语／范围 `locked_claims`，以及 `review_status`。
- 附录与引用：`appendix / citation_index`；内部问题和客户可见待确认事项分别标记。

逐页大纲确认和内容审核记录随包传递。制作前读取所选 PPT Skill 的当前入口，根据其实际接收方式生成 Markdown、任务说明或结构化文件；能力、模板、图片／对象编辑性和导出形式均按实际工具确定。

### 7.2 PPT Skill 的修改权限

允许调整排版、配色、字形、图标和不改变含义的文字压缩；不能新增事实、能力、收益、价格、交期或删除重要限定条件。需要拆页、合页或调整论述时，返回变更建议，更新内容包和页面映射，再制作新版本。细小排版调整在已有授权内执行。

素材是否发送外部生成服务按用户已有授权和素材使用范围处理。接口提供字段白名单，只传制作需要的内容，不把内部销售判断、联系方式、未授权客户原件或完整内部澄清台账一并打包。

### 7.3 PPT Skill 返回的结果

返回实际 PPTX 及按约定提供的 PDF／预览、输出文件哈希、页面顺序与 `slide_id` 映射、源内容包版本、采用模板、可编辑性说明、未解决制作问题。若 Skill 无法原生返回这些元信息，由总控基于实际文件补充，不能凭文件名推断。

PPT Skill 的视觉 QA 可作为证据，但售前审核仍要核对实际文件中的关键结论、数字、图片和限定条件。文件存在、可下载、可打开、视觉正确、业务批准及已外发是不同事实。

### 7.4 首次本地适配验证

首轮使用本地 `ppt-master-plus` 4.5.0，制作入口传逐页内容包 Markdown，返回原生可编辑 PPTX；总控补充内容包版本/hash、逐页映射、实际输出hash及审核记录。保持外部PPT接口可替换，不把本机Python路径或模板作为售前Skill硬依赖。实际验收以PowerPoint原生打开及导出PDF为证据；仅SVG检查通过不足以证明最终文件可读。详细结果与未验证范围见[模拟验证记录](2026-10-11-presales-ppt-master-plus-validation.md)。

## 8. 方案验收审核的专门设计

### 8.1 三种调用时点

| 模式 | 审核对象 | 判定目标 |
|---|---|---|
| `direction` | 需求摘要、脑图、候选方案 | 是否理解客户、主线是否成立、关键未知是否显式；不要求最终 PPT。 |
| `content` | 方案蓝图、逐页大纲／内容包和依据 | 是否可交给 PPT Skill 制作；关键需求、能力依据和承诺是否完整。 |
| `delivery` | 当前内容包、真实 PPT 和页面渲染 | 内容是否忠实落入文件，关键页面是否可读，问题是否关闭，适合何种使用范围。 |

### 8.2 检查维度

1. **需求覆盖**：重要需求逐条对应方案机制与实际页面，结论为满足、部分满足、未满足、未知或有依据的不适用。提到关键词不算满足。
2. **事实和证据**：客户背景、产品能力、案例、数字、日期有可回查来源，来源版本适用，推断不冒充事实。
3. **方案可行性**：业务过程、能力组合、接口／数据／安全前提、责任、实施顺序和验证方式相互一致；需求深度与本次售前阶段匹配。
4. **价值与承诺**：价值对应客户目标；测算标清基线、公式和假设；工期、范围、报价与非标承诺有相应依据及授权，未知项不藏入正式结论。
5. **汇报逻辑**：面向实际受众，问题—方案—依据—行动衔接清楚；公司产品材料服务于客户问题，结尾明确希望取得的决定。
6. **跨页一致性**：主体、产品版本、数量、单位、范围、阶段、架构关系和术语一致；摘要不能夸大正文。
7. **实际文件与视觉**：文件可复开、顺序正确、无漏页、无溢出遮挡、关键图文可读、数字和限定条件未丢失；实际编辑性与承诺相符。
8. **使用范围**：客户可见文件没有内部备注、其他客户未授权资料或不应公开的信息；交付版本、受众和已授权动作对应。

不要用一个总分抵消严重问题。没有依据的关键能力承诺、错误客户事实、关键范围冲突、重要需求无响应或不可读的关键页，应阻止当前用途的交付建议。一般文字精简等问题可给 conditional，但必须说明影响、处理人和适用用途；不能把 conditional 简写为“审核通过”。

### 8.3 整改闭环和独立性

每个发现关联来源、需求／方案／页面 ID、实际页码、严重度、责任角色和具体动作。事实不明交澄清，材料不足交选材，方案不成立交设计，表述问题交写作，排版问题交 PPT Skill。整改后读取新文件及证据再关闭；“已生成整改建议”不是“整改完成”。

能安排独立审阅时，由未参与该版本写作的人或独立 Agent 执行关键内容复核；记录实际评审身份及方式。工具条件不支持时明确标为自检结果，不虚构独立审核。机器结构校验、模型语义评审、实际渲染检查和业务负责人确认分别记录。

审核输出必须给出：审核版本及输入范围、检查方法、覆盖结果、阻塞／一般问题、未检查事项、整改复核证据、允许建议的使用阶段。最终报告由当前证据支持，不自动产生“客户已接受”的结论。

## 9. 与已有套件的复用和区别

| 参考能力 | 本设计吸收的做法 | 售前需要调整的边界 |
|---|---|---|
| 投标 `bid-source-intake`、`bid-requirements` | 来源定位、读取覆盖、原子需求、条件和冲突保留 | 增加角色诉求与探索性需求，不默认存在招标原文。 |
| 投标 `bid-evidence-matching` | 材料适用性、候选与已核实区分、版本和来源 | 重点检查产品版本、能力成熟度、组合边界与案例适用性。 |
| 投标 `bid-review-remediation` | 要求／证据／实际正文逐项对照、整改后重新评审 | 主要对象是客户问题、方案可信度与承诺；不套用资格／评分／废标结论。 |
| 投标 `bid-orchestrator` | 项目状态、任务范围、版本变化、断点继续 | 先采用轻量文件编排，避免照搬全部投标流程。 |
| 咨询 `transformation-storyline-builder` 与 PPT 契约 | 叙事主线、逐页内容包、讲什么与如何呈现分离 | 允许阶段适当的售前探索稿，不强制完整咨询成果和 4A 审批。 |
| 咨询 `consulting-quality-review` | 证据、逻辑、口径、阶段适配、独立审阅 | 针对本次售前范围评审，不把企业规划验收项全部变为售前前置。 |

两个参考套件中已经有质量评审能力；本设计新增的售前审核 Skill 复用其方法，专门定义售前对象、输入和验收规则，不将投标评审或咨询评审直接改名使用。

## 10. 首版实施与验证建议（尚未执行）

实施先打通一条主线：一组明确为模拟的混合材料，完成“材料→需求→脑图→澄清回写→能力匹配与方案→逐页大纲→内容包→既有 PPT Skill→实际文件审核→整改复核”。这条主线成功后再添加行业包、资料库连接和并行内容编写。

首版只建设上述技能说明、必要的共用交接约定和少量模板。结构化校验器围绕实际稳定字段编写；不提前建立复杂通用运行时。PPT 使用当前已有技能，通过一个具体适配路径验证，不同时兼容全部渲染器。

至少用以下场景验证业务行为，而非只检查 Skill 文件格式：

| 场景 | 预期行为 |
|---|---|
| Word + 扫描 PDF + 现场照片 + 会议记录 | 来源可定位，未读区域可见；照片观察不升级为设备能力证明。 |
| 两名客户角色对范围表述冲突 | 保留冲突和各自来源，提出可决策问题，不静默择一。 |
| 旧版产品 PPT 与当前能力说明冲突 | 标明版本差异；不把路线图功能当作现有标准能力。 |
| 接口信息不足或没有收益基线 | 生成明确限定的候选方案及澄清项，不编造兼容性或 ROI。 |
| 脑图和大纲已确认后新增需求 | 只更新受影响成果，旧审核失效；已有无关确认不重复索取。 |
| 同一套能力用于管理层汇报与技术交流 | 依据同一方案事实调整主线、详略和附录，不形成冲突承诺。 |
| 仅提供一份已有 PPT 要求审核 | 完成可核验范围的独立审核，明确客户需求覆盖无法确认。 |
| PPT 制作时丢失单位、限制条件或产生溢出 | 实际文件审核发现问题，整改并重新读取当前文件后才关闭。 |
| 其他客户案例混入或内部备注泄漏 | 标出具体素材／页面并阻止相关客户版本的交付建议。 |

验证记录分别报告结构、模型行为、PPT 文件回读、视觉和业务确认；合成演练不代表真实客户验收。本轮只完成设计文档检查，上表均为后续待执行用例。
