# 软件定制开发与系统集成：项目交付 Skills 设计

日期：2026-10-11。状态：设计建议，待业务评审；本轮未创建或安装交付 Skills，未生成真实项目文件，未进行项目运行验收。

## 1. 目标与范围

用户已明确第一版面向**软件定制开发与系统集成**。建立从售前/合同交接、项目启动、调研、业务蓝图、实施设计、开发集成、测试、上线、验收到质保移交的完整工作方法，同时贯穿进度、资源工时、成本差旅、风险问题、质量和变更管理。

这套能力既要回答“当前阶段应该做什么、交付什么”，也要回答“项目还剩多少工作、预计何时交付、预计成本多少、谁需要解决什么问题”。模板是工作结果的载体，不能只做一套空白文档生成器。

建议把项目管理组织成：

- **阶段主线**：交接 → 启动 → 调研 → 蓝图 → 设计 → 开发集成 → 测试 → 上线 → 验收 → 质保与收尾。
- **三条核心控制线**：进度与里程碑；资源工时与成本；风险与质量。范围、变更、协作和证据贯穿三条线。
- **共同依据**：合同义务、需求基线、计划基线、成本预算、交付物清单、验收规则，以及它们的有效版本。

初版采用本地项目文件夹、结构化台账和可阅读文档。后续可接飞书、任务系统、代码仓库和财务系统，但项目管理方法不依赖先建设一个平台。

项目配置至少区分：固定总价、按工时计费、混合计费；定制开发、系统集成、混合交付；分阶段/迭代交付；合同约定的验收与质保方式。行业监管、驻场、安全和数据要求作为项目约束补充。

## 2. 方案取舍与现有 Skills 边界

| 组织方式 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 单个大型交付 Skill | 入口简单 | 更新一次周报也加载全流程，职责和状态易混淆 | 不作为主体方案 |
| 一个总控 + 独立业务 Skills + 共享模板/台账 | 可完整推进，也可只做调研、蓝图、周报或验收 | 需要明确产物契约和唯一写入责任 | **推荐** |
| 先建项目管理平台再挂 Skills | 多人协作与权限空间更大 | 首版投入大，流程尚未验证就固化产品 | 真实项目验证后再判断 |

现有仓库能力与新套件的关系：

| 已有能力 | 向交付提供什么 | 新套件负责什么 |
|---|---|---|
| 商机分析 `opportunity-analysis-skill` | 客户、联系人、需求线索、决策链、跟进历史 | 核实实际项目角色、合同范围和交付责任；商机概率不作为项目履约状态 |
| 投标 `bid-skills-suite-v1.0.0` | 技术响应、承诺、偏离、报价/交付假设中的授权内容 | 建立合同义务映射；中标或提交不等于启动条件齐备 |
| 售前 `presales-solution-skills` | 需求、方案、产品能力、限定条件、未决事项 | 对照签约文件重新核对交付范围；售前方案不自动成为实施基线 |
| 转型咨询套件 | 现状、目标业务/架构、路线图、咨询结论 | 复用适用成果；实施级字段、接口、迁移、上线设计按实际范围补齐 |
| `requirements-to-delivery` | 需求到设计、开发任务、测试的工程追溯链 | 新套件管理客户项目、工期预算和交付确认；工程内容复用，避免两套需求/任务主账 |
| 文档、PPT、绘图、原型和 UI 验收 Skills | 内容渲染、效果图、可交互原型、实际文件检查 | 交付套件决定内容与事实，外部工具负责生成与检查具体载体 |

共享 ID 应映射复用，避免给同一需求重新编号后失去来源。跨套件适配在实施时验证；当前读取到已有套件说明，不据此宣称互联已经打通。

## 3. 端到端阶段与完成依据

阶段可迭代、并行或分批；例如一批模块进入开发时另一批仍在调研。但每批工作必须明确采用哪个需求/设计版本，不能把项目整体状态简化成一个“进行中”。

| 阶段 | 主要输入 | 关键工作 | 核心产物 | 进入下一阶段的依据 |
|---|---|---|---|---|
| S0 交接与履约核对 | 合同、技术协议、附件、投标/售前资料 | 提取义务、交付边界、日期、验收/付款条件、客户配合项；核查冲突缺件 | 合同义务矩阵、交接记录、范围清单、待澄清项 | 交付负责人知道做什么、何时做、谁配合、如何判定完成；未知项可定位 |
| S1 启动与基线 | S0 产物、人员/预算信息 | 定义组织职责、沟通机制、总体计划、预算、风险和启动议程 | 项目章程、启动会材料与纪要、Master Plan v1、预算 v1 | 有效责任人、可执行近期任务、关键依赖；实际确认单独登记 |
| S2 调研与需求确认 | 合同范围、现有系统/流程、关键人 | 调研计划、访谈、录音/纪要、需求提炼、冲突澄清、优先级与验收条件 | 调研计划、调研底稿、需求规格/台账、资料缺口 | 重点流程、规则、数据、异常、非功能要求可追溯；遗漏与分歧显式保留 |
| S3 业务蓝图 | 调研与需求候选基线 | 描述现状/目标流程、角色职责、范围与系统分工；组织评审 | 业务蓝图、流程图、需求覆盖矩阵、评审与确认记录 | 指定版本与指定范围得到有权客户代表确认，或明确为讨论稿 |
| S4 实施设计与计划细化 | 有效蓝图、技术约束 | UI/字段/权限/状态、架构、接口、迁移、安全、测试和部署设计；细化 WBS | 实施设计包、原型、接口/数据规范、迭代计划、测试计划、实施蓝图确认包 | 按模块/批次确认流程、UI/字段/权限、接口/数据与验收场景；按约定由有权客户代表确认，或有明确的授权先行依据；工作包有完成规则和资源 |
| S5 开发、配置与集成 | 工作包、设计、环境与接口 | 跟踪开发/配置、代码评审、构建版本、联调、缺陷、外包交付 | 工作包交付记录、版本清单、联调记录、缺陷台账 | 交付版本与需求/设计对应，具备测试证据；“代码合并”不能代替业务完成 |
| S6 测试与客户验证 | 可测试版本、测试数据/环境 | 功能/集成/权限/性能/安全/迁移验证；组织 UAT 与整改复测 | 测试报告、UAT 记录、缺陷关闭/接受记录 | 适用质量标准达成；残留缺陷有实际处置人和接受依据 |
| S7 上线与移交 | 验证结果、上线前提 | 培训、切换、迁移核对、备份回滚、监测、应急和值守 | 上线方案/检查表、切换记录、培训记录、运维移交包 | 上线授权有效、实际切换成功且业务核对完成；移交方确认接收范围 |
| S8 里程碑与最终验收 | 合同条款、交付清单、版本、客户验证 | 按合同条件组织验收，核实证据、签署、遗留事项及付款触发条件 | 里程碑确认单、交付清单、验收报告/单、遗留事项清单 | 有效客户确认对应具体版本/范围；内部评审通过与客户签署分别登记 |
| S9 质保与项目收尾 | 验收结果、质保约定、实际成本 | 移交质保责任、处理缺陷、结算核对、资源释放、复盘归档 | 质保台账、移交确认、成本总结、复盘、归档索引 | 行政收尾、质保移交、质保结束分别判断；未完义务持续跟踪 |

里程碑确认可发生在任何阶段。合同若以蓝图签署、上线、试运行结束或分批验收作为付款触发，应逐项建关联，不能统一等到最后才处理。

## 4. Skill 拆分：1 个总控 + 24 个业务 Skill

拆分依据是可独立触发的业务工作和产物责任。一个 Skill 可以生成多种模板，同一模板也可以生成多个客户版本；不按每张表单创建 Skill。

### 4.1 总控与项目建立

| 编号 / Skill | 触发与输入 | 核心处理 | 主要输出 | 完成依据 / 异常处理 |
|---|---|---|---|---|
| 01 `delivery-orchestrator` | 开始/继续项目，指定项目目录或单项任务 | 恢复当前有效版本；判断阶段、阻塞、下一工作；生成有边界的任务卡；登记结果 | 项目状态、下一步任务卡、产物索引、待决事项 | 依据可回读；缺资料可先整理草稿；总控不代替专业结论或客户批准 |
| 02 `delivery-source-intake` | 新增合同、文档、表格、截图、邮件或录音 | 保存原件和来源；提取正文；记录页码/工作表/时间定位与读取缺口 | 来源登记、可读底稿、读取覆盖记录 | 未转录录音、扫描页和损坏附件标明未读，不能视为已解析 |
| 03 `delivery-contract-handover` | 售前转交付、补充合同/技术协议 | 提取义务及范围；对照售前承诺；登记验收、付款、质保、客户配合及分歧 | 合同义务矩阵、交接清单、范围内外清单 | 冲突按合同约定与实际授权澄清；不自行断定文件法律优先级 |
| 04 `delivery-initiation-kickoff` | 项目启动、团队调整；合同交接/人员输入 | 项目目标、职责与授权、客户关键人、沟通升级机制、启动议程 | 章程、角色/RACI、启动会内容包、启动纪要与行动项 | 谁负责/确认清楚；PPT 由已有渲染能力生成；拟定人员不写成已到位 |
| 05 `delivery-master-planning` | 制定总计划、重排计划；范围/资源/依赖输入 | 分解 WBS、工期与工时、依赖、日历、里程碑和关键链路；滚动细化近期任务 | Master Plan、WBS、里程碑、资源需求和计划版本 | 依赖及估算条件完整；日期未知保留待定；重排不覆盖原基线 |

### 4.2 调研、蓝图与设计

| 编号 / Skill | 触发与输入 | 核心处理 | 主要输出 | 完成依据 / 异常处理 |
|---|---|---|---|---|
| 06 `delivery-discovery-planning` | 准备调研；范围、现状、关键人输入 | 设计访谈对象/时间/主题/方法、问题、客户准备材料和预计产物 | 调研计划、访谈提纲、资料清单、调研底稿模板 | 每场有目标、双方责任和输出；关键人缺位/未排期显式标记 |
| 07 `delivery-meeting-records` | 调研会、周会、设计会录音/文字输入 | 区分发言、事实、建议、决策与待确认事项；提取行动项/责任/期限 | 会议纪要、行动项、待确认决策及来源引用 | 未听清/说话人不明不猜；纪要草稿不自动成为客户确认 |
| 08 `delivery-requirements-baseline` | 需求整理/复核；合同、纪要、底稿输入 | 原子化需求、规则、优先级、来源、范围和验收标准；澄清冲突 | 需求规格、需求台账、需求覆盖及确认记录 | 保留不同角色分歧；基线后的新增/修改进入变更评估 |
| 09 `delivery-business-blueprint` | 形成/修订蓝图；有效需求和流程底稿 | 组织现状/目标流程、业务角色、系统边界、业务规则和例外；组织覆盖评审 | 蓝图、流程图规格、覆盖矩阵、评审问题与确认包 | 每条关键需求有落点；讨论稿、内部通过、客户确认分开 |
| 10 `delivery-solution-design` | 实施架构与详细设计；蓝图/技术约束输入 | 设计组件、部署、权限、非功能指标、安全机制、容灾/运维和技术取舍 | 实施设计总册、设计决策、非功能验证要求 | 没有证据的性能指标保留目标与验证条件；不凭行业惯例补造客户要求 |
| 11 `delivery-ui-field-design` | UI/字段/权限设计；流程、需求与设计输入 | 页面/交互、字段约束、状态转换、角色权限、异常与原型设计 | 页面规格、字段字典、权限矩阵、原型任务/回读记录 | 必填、精度、校验、显隐、读写、默认、来源和异常定义可实施；效果图不是功能实现 |
| 12 `delivery-integration-data` | 接口/迁移设计与联调；系统清单/数据输入 | 接口协议、认证、字段映射、幂等/重试、错误补偿、迁移核对、各方责任 | 接口清单/规范、映射表、联调记录、迁移方案和核对结果 | 第三方版本/环境/权限/负责人未知要显式阻塞；不以连通测试代替业务一致性 |

### 4.3 实施、质量与移交

| 编号 / Skill | 触发与输入 | 核心处理 | 主要输出 | 完成依据 / 异常处理 |
|---|---|---|---|---|
| 13 `delivery-work-package` | 下发/跟踪开发配置外包工作；WBS、设计输入 | 明确交付范围、版本、完成规则、依赖和责任；关联代码/构建/交付证据；按授权调用工程能力 | 工作包任务卡、交付记录、迭代清单 | 管理执行契约；不声称技能自动完成代码开发；开发完成与验收完成分开 |
| 14 `delivery-quality-testing` | 测试规划、质量检查、UAT/缺陷整改 | 按需求/风险制定测试；汇总实际执行、缺陷、复测和证据；核查版本与环境 | 质量计划、测试用例/报告、缺陷台账、UAT 包 | 未执行与通过分开；阻塞缺陷不靠修改报告关闭；接受残留须记录实际责任与依据 |
| 15 `delivery-go-live-transition` | 准备/执行上线；候选版本、测试、环境输入 | 检查准入、窗口、备份/回滚、迁移、业务核对、监测和值守；记录结果 | 上线方案、检查表、切换/回滚记录、观察期报告 | 计划与实际动作分开；生产动作依当前授权执行，失败按回滚方案处理 |
| 16 `delivery-training-handover` | 用户培训、管理员/运维交接 | 按角色准备教材、操作/运维手册、演练和接收清单；交接资产位置 | 培训资料/记录、用户手册、运维手册、移交记录 | 培训出席不等于掌握；密码不写入文档，访问移交记录对象与完成证据 |

### 4.4 贯穿全程的管理与收尾

| 编号 / Skill | 触发与输入 | 核心处理 | 主要输出 | 完成依据 / 异常处理 |
|---|---|---|---|---|
| 17 `delivery-progress-control` | 更新进度、延期预警；计划、交付事实输入 | 比较基线/实际/预测；分析依赖与延期影响；提出可行纠偏选择 | 进度台账、里程碑预测、偏差及纠偏建议 | 工时消耗不冒充完成度；无可靠依赖不输出伪精确关键路径 |
| 18 `delivery-resource-timesheets` | 人员排班、工时填报/审核；资源计划输入 | 人员可用量、并行分配、实际工时、加班/差旅时间口径、外包工时核验 | 资源计划、工时台账、审核差异、剩余工作估算输入 | 工时均关联工作包/活动；拒绝重复计时；未填报不记作零；个人费率限内部可见 |
| 19 `delivery-cost-expenses` | 预算、成本预测、差旅/采购核对 | 人工、采购、外包、差旅、其他成本归集；比较预算/发生/承诺/完工预测 | 预算、费用台账、成本预测、预算偏差和付款条件跟踪 | 申请/发生/报销/付款不重复计成本；不代替财务记账或支付审批 |
| 20 `delivery-risk-issue` | 识别/复核风险与已发生问题 | 分开管理不确定事件和实际阻塞；评估影响、触发信号、措施、责任与升级 | 风险台账、问题台账、依赖清单、升级建议 | 风险转问题保留关联；关闭需处置/验证证据；分级阈值按项目约定 |
| 21 `delivery-change-control` | 范围/设计/工期/成本/验收条件变化 | 对照有效基线，分析影响、准备选项、登记决策并协调领域主账修订 | 变更申请、影响分析、实际决策记录、基线修订包 | 批准与生效分开；领域 Skill 各自修订，总控回读完整后激活；未批准项保持独立 |
| 22 `delivery-reporting` | 项目周报、周会、月报/管理汇报 | 固定统计截止日；从台账提取事实/预测/待决项；输出内外部不同视图 | 周报、周会议程/汇报内容包、管理摘要 | 报告不另建事实主账；草稿/未核实数据可见；外发权限另行判断 |
| 23 `delivery-milestone-acceptance` | 蓝图确认、阶段交付或最终验收 | 按合同/有效变更映射交付物和证据，组织检查、遗留项、确认人与确认范围 | 里程碑确认、验收包、交付清单、付款触发条件核对 | 证据精确关联版本；内部通过不等于客户签署；满足付款条件不等于开票或到账 |
| 24 `delivery-closure-warranty` | 项目收尾、质保移交/结束 | 检查剩余义务、成本、外包/采购、访问/资产移交、资源释放和经验复盘 | 收尾报告、质保台账、知识沉淀、归档/移交索引 | 有主责人才能移交遗留项；按合同区分行政结项、质保移交与全部履约结束 |
| 25 `delivery-artifact-review` | 关键成果交付前、整改复核 | 核查范围、追溯、跨文档一致性、敏感信息、实际文件打开/渲染和有效版本 | 质量审查单、整改记录、版本化可交付建议 | 结构检查/语义评审/实际文件回读分开；审查结论不充当客户授权 |

每个技能实施时采用统一任务卡：项目与目标、有效输入版本、执行范围、处理要求、输出位置、完成证据、未决问题、受影响下游。仅加载本阶段需要的模板和参考。

## 5. 模板体系：关键模板的字段设计

模板统一包含：项目 ID/名称、文档 ID/版本/状态、负责人、统计截止日或适用期间、来源依据、审核/确认记录、修订历史、内部/客户可见范围。下列为字段与章节规格，本轮不制作可直接交付的 DOCX/XLSX/PPTX 文件。

### 5.1 项目启动会模板

1. 项目背景、业务目标及成功标准：区分合同要求、客户期望与待确认目标。
2. 合同/技术协议依据、交付范围及明确不包含项；涉及哪些系统、组织与站点。
3. 项目组织：客户发起人、项目经理、业务负责人、IT/安全、第三方；供应商项目经理、业务分析、架构、开发、测试、实施与运维；职责和确认权限。
4. 总体路径、主要交付物、里程碑、关键依赖和近期两周安排。
5. 客户配合清单：关键人时间、环境/账号、接口文档、数据样本、审批、验收代表。
6. 调研与蓝图的推进方法、评审和需求变更方式。
7. 周会、周报、问题升级、文件命名与确认渠道。
8. 初始风险、当前待决事项和行动项。

配套：启动会议程、启动 PPT 内容包、参会/职责确认表、启动纪要和行动项。人员费率、内部毛利、内部绩效评价不进入客户版启动材料。

### 5.2 客户调研计划与底稿模板

| 字段组 | 必备内容 |
|---|---|
| 安排 | 调研 ID、主题、日期/时间段、地点/线上方式、状态、预计时长 |
| 对象 | 客户部门、姓名/角色、业务责任、可确认事项；我方主持、记录、专业人员 |
| 目标 | 需要弄清的业务问题、关联流程/需求/合同范围、预期决策和输出物 |
| 内容 | 当前流程、目标场景、业务规则、异常处理、数据/报表、权限、系统接口、非功能约束 |
| 双方准备 | 客户需提供的制度/表单/样本/系统演示/接口材料；我方访谈提纲/原型/已知问题 |

录音先转录再提炼纪要，保留可定位时间段；没有工具时如实标注待转录，不能从录音文件名推导会议内容。主持人观点、参会者建议与正式决策分别记录。

### 5.3 蓝图确认模板

业务蓝图回答“业务如何运行、系统做什么”；实施设计回答“如何具体实现和验证”。小项目可合册，大项目分册，但映射必须保留。

**A. 业务蓝图册**：

- 项目目标、依据、范围内外、术语和关键假设。
- 现状流程/问题、目标端到端流程、业务角色与职责、跨部门协作。
- 每条流程的入口/出口、触发、正常与异常分支、审批规则、单据/报表。
- 需求清单、优先级、标准/配置/定制/第三方分工、验收条件与覆盖。
- 系统边界、关键数据对象、集成清单、客户配合项。
- 未决事项、争议/排除项、版本变化、评审意见、确认范围与确认依据。

**B. 实施设计附件**：

- UI 页面及交互：页面 ID、关联流程/需求、角色、状态、按钮、提示、异常与原型链接/版本。
- 字段字典：字段 ID/名称、业务含义、类型/长度/精度、单位、必填、默认值、枚举、唯一性、校验、显隐/读写权限、数据来源、计算规则、接口映射、敏感性、异常展示。
- 业务状态机与权限矩阵：谁可以在什么状态执行何种操作，失败后如何恢复。
- 报表规格：口径、维度、筛选、计算、权限、刷新频率、导出要求。
- 接口与数据设计：见 5.4；架构、部署、安全、性能、可用性、迁移与回滚需求。
- 可测试验收场景：前置条件、输入、步骤、预期结果、证据和责任人。

**C. 确认包**：确认单标明文档 ID/版本/哈希、适用模块、双方确认人/角色、确认日期与渠道、保留意见、未决项处置、后续变更入口。客户审阅中、客户有条件确认与全部确认分别记录。

确认分业务蓝图和实施蓝图两个时点，亦可合并评审。实施蓝图按模块/批次包含 A 的业务内容、B 的页面/字段/权限、接口/数据和验收场景，由约定的有权客户代表确认后进入该批次开发。若合同或已授权安排允许先行开发，登记授权人、范围、采用版本、未确认项与返工处理依据；不把探索原型升级为已批准实施。条件确认只允许推进不受未决项影响的工作，或已有明确授权处置的部分。

### 5.4 接口、数据迁移与联调模板

- 接口：双方系统/版本/负责人、业务目的、方向与触发、协议/认证/环境、频率/容量、字段映射、时间/编码/单位、幂等、超时/重试、错误码/补偿、日志与监测、测试样本、成功条件。
- 联调：版本、环境、时间、参与方、场景、请求/响应的脱敏证据、业务核对、缺陷、复测与结论。
- 迁移：数据来源/范围、清洗与映射、样本验证、试迁移、全量/增量方案、条数/金额/关键业务一致性核对、备份/回滚、冻结窗口和数据责任人。
- 第三方依赖：资料、接口、许可、环境、网络、测试数据、交付日期、负责人及升级路径。

### 5.5 Master Plan 与周报模板

**Master Plan** 字段：工作包 ID、阶段、范围/需求 ID、任务/交付物、完成规则、负责人、参与方、前置依赖、工作日历、基线起止、当前计划起止、实际起止、工作量估计、资源需求、剩余工作、完成证据、预测完成日、里程碑、风险/变更关联、版本。

三种日期必须并存：原始/当前批准基线、最新预测、实际。迭代计划可细化任务，但不能悄悄修改合同里程碑。关键路径仅在依赖/工期/日历足够可靠时计算，否则输出待核实链路。

**周报客户版**：统计期间与截止日、总体判断及依据、上周计划/实际、交付物与确认情况、里程碑偏差、本周/下周计划、问题风险、客户配合、需要决策事项和责任/期限。

## 6. 共享数据与追溯关系

文档、PPT、表格和报告是同一组项目对象的不同视图。建议以结构化 JSON/CSV 为台账交换格式，Markdown 为内容底稿，Word/Excel/PPT/PDF 为按需输出；最终格式依据用户与客户模板选择，不强制重复维护多套事实。

最小对象包括：项目、合同义务、来源证据、人员/职责、需求、流程、设计/页面/字段、接口/数据、工作包、里程碑、版本、测试/缺陷、工时、费用/预算、风险/问题、变更、行动/决策、交付物、确认/验收与质保事项。

主追溯链：

`合同义务 → 调研证据 → 需求 → 蓝图/设计 → 工作包 → 版本/交付物 → 测试/UAT → 里程碑/验收`

辅助关联：工时/成本归属工作包；工作包属于阶段/里程碑；风险/问题/变更可关联任一对象；客户确认绑定具体文档版本/范围；每个工作包可以分配多人，每个里程碑可以覆盖多个工作包。

统一头字段建议：`project_id / artifact_id / revision / kind / owner / source_refs / input_versions / content_hash / visibility / status / as_of / review_refs / confirmation_refs`。成熟的已有对象 ID 保留，并建立映射。源材料、产物、确认证据分别保存。

状态分开记录：

- 内容：草稿、待评审、已评审、已发布版本、已失效、已替代。
- 业务确认：不需要、待确认、有条件确认、已确认、被退回；含确认人、权限依据、版本、范围、时间和渠道。
- 执行：未开始、进行中、阻塞、已完成；完成需匹配任务定义的证据。
- 对外动作：已准备、已获授权、实际已发送/已上线；从实际结果更新。

新增录音不必让全项目失效；识别其引起的需求/设计变化后，标记受影响的设计、计划、用例与确认范围需要复核。正式基线在变更未获授权前保持有效，候选修订独立保存。客户确认的旧版本保留历史证据。

### 6.1 主账责任与变更生效

| 主账 / 对象 | 唯一内容责任 | 其他能力的关系 |
|---|---|---|
| 需求、业务蓝图 | 08、09 分别维护对应对象 | 工程 Skill 消费同一 ID/有效版本并提交候选修订，不另建独立需求主账 |
| 实施架构、UI/字段、接口/数据 | 10、11、12 分别维护对应设计 | 工程工具生成内容时，由对应领域 Skill 整理登记，不并行覆写 |
| 工作包、测试/缺陷 | 13、14 分别维护对应对象 | 代码/任务/测试系统作为执行证据来源；指定同步方向，冲突进入核对 |
| Master Plan、资源/工时、预算/费用 | 05、18、19 分别维护主账 | 17 读取计划与事实提出预测/纠偏，计划修订归 05；22 只生成视图 |
| 变更决策、验收确认 | 21、23 分别维护对应记录 | 不代写其他领域主账，不创造客户决策 |
| 项目索引、有效版本集合 | 01 总控单写登记 | 25 复核候选成果及依赖一致性，不能代替业务授权 |

这里的唯一责任是对象级责任，非要求同一人执行所有工作。与 `requirements-to-delivery` 组合时，在任务卡明确当前主账路径和写入职责；它可提供分析/设计/开发产物，但不能同时运行另一条独立的需求到验收主线。

变更落地顺序：登记实际决策 → 状态为“已批准、待应用” → 08—14 修订受影响内容/工作/用例 → 05/18/19 更新受影响计划/资源/预算 → 23 更新确认/验收映射 → 25 复核 → 01 回读引用和版本后登记新的有效版本集合，将变更置为“已生效”。不涉及的对象跳过。

修订先写候选版本；中途失败记录“应用未完成”及已写/待写对象，旧有效版本集合保留，新工作不得混用两组基线。恢复时按对象版本继续，不重复追加工时/费用。首版通过单写登记与一次更新有效版本清单实现，不建设分布式事务系统。

## 7. 三条管理线如何运作

### 7.1 进度与里程碑

- 从合同日期、交付物和依赖生成初版 Master Plan，启动阶段可用估算，但必须可识别。
- 调研/蓝图确认后细化；每周基于实际交付、阻塞、剩余工作和资源可用量更新预测。
- 每个工作包定义完成规则，例如“接口联调通过并有业务核对记录”；不能只用“负责人说完成 90%”。
- 延期分析给出受影响里程碑、依赖与可选处理：调整顺序、资源、范围/批次或日期；实际决策进入变更/决策记录。
- 日历、工期和人时分开。两人工作一天不能直接当作工期两天，多人投入也不保证线性缩短工期。

### 7.2 人员、工时与成本

以下为建议的**项目管理口径**，实施时与公司财务口径对齐：

- 人工发生估计 = 按统一口径可计入的实际工时 × 对应人员/角色的有效内部成本费率。未审核工时单独列为暂估，不能静默排除导致低估。
- 内部人员采用工时与内部费率估计成本；外包人员按合同约定，以结算/应计记录作为成本实际来源，工时用于进度与结算核验。按工时计价的外包可由核验工时与合同费率形成暂估，账单/结算到达后冲销或替换暂估，不能再新增一份成本。
- 每项成本以稳定 `cost_item_id` 关联工时、采购/差旅和结算证据；暂估、发生/应计、账单、支付是同一事项的状态/核对，不是多个可累加成本。采购按约定发生依据入账，差旅按实际发生及核验口径归集，财务实际可回写校准管理估计。
- 完工预测成本 = 已发生成本 + 剩余预计成本。
- 剩余预计成本包含“尚未发生的采购/外包等承诺”及“其他剩余工作预计”，两部分去重；发生后从承诺余额转入已发生，不重复累计。
- 成本偏差 = 完工预测成本 − 当前批准预算；正值表示预计超预算。
- 费用申请/预算占用、实际发生、报销、支付分别是状态/事实；同一笔差旅不能因经历四个状态累计四次。
- 固定总价项目关注预计成本和合同收入基准下的项目贡献；按工时计费项目另管可计费、客户认可与实际计费工时，不能把全部投入当收入。
- 需要展示预计贡献时，收入基准须标明合同/已批准变更、税及币种口径；使用统一直接/分摊成本范围。不自动称为财务毛利，不等同于确认收入或现金流。
- 成本和应收条件联动但分账：客户验收、开票、付款条件达成、实际收款各自有证据。

必要的活动分类包括需求/设计/开发/测试/实施/管理/培训/返工/差旅。返工要关联原因：缺陷、范围变化、客户材料不完整或第三方变动，不能只归因到人员效率。

### 7.3 风险、问题与质量

- 风险描述尚未发生的不确定事件；问题描述已经发生的阻塞/偏差；缺陷是质量问题的一类，主账由测试质量维护，风险问题台账引用，避免重复关闭。
- 每项记录原因、影响对象、程度、负责人、应对/解决动作、截止日、触发/升级条件和当前证据。
- 质量前置到需求可测试性、设计一致性、代码/版本、接口业务核对与迁移一致性，不能只在最终验收检查文档齐全。
- 缺陷关闭需复测；客户接受遗留项需明确接受人、版本、业务影响、补救责任/期限与验收处理依据。
- 风险热度和红黄绿阈值在启动时设定，周报解释判断依据。未配置阈值时给出事实与建议等级，不伪装成公司既定政策。

### 7.4 一个跨线场景

客户在蓝图确认后要求新增一个审批环节：

1. 纪要保留原话/来源，需求形成候选修订，已有确认版本不变。
2. 变更分析关联流程、页面字段、权限、接口、用例与培训文档。
3. 工作包估算新增和返工工作；资源/工时提供可用量与估算依据；成本分析形成增量预测。
4. 计划分析对依赖与里程碑的影响；风险分析说明不做/延期/临时方案的影响。
5. 有权人员批准后先记“已批准、待应用”，按 6.1 修订各主账并复核/回读，完整后激活范围/计划/预算版本集合，登记客户确认范围；失败保持旧有效集合，被拒绝则保留原基线。
6. 实施、测试、交付按新版本留证；周报读取同一组状态，验收检查实际范围。

这条路径是后续评测的重点，不能只验证“成功生成一张变更申请表”。

## 8. 项目目录与归档

以下是结构规格，本轮不初始化项目目录。空目录无需预创建；有实际产物时再生成。

```text
project-<项目编号>/
  README.md                         # 当前状态、入口、下一步
  00-control/                       # 项目画像、产物索引、有效版本、决策/确认
  01-contract-handover/              # 合同/技术协议/附件、交接、义务与范围
  02-initiation/                     # 项目章程、组织、启动会
  03-plan/                           # Master Plan、WBS、里程碑、基线快照
  04-discovery/                      # 调研计划/底稿、录音引用、纪要、材料
  05-requirements-blueprint/          # 需求、业务蓝图、客户确认
  06-design/                         # 架构、UI/字段/权限、接口、迁移、原型
  07-development-integration/        # 工作包、版本、联调、工程库引用
  08-quality-uat/                    # 质量计划、测试、缺陷、UAT
  09-go-live-handover/               # 上线、回滚、培训、运维接收
  10-project-control/                # 风险/问题/依赖、变更、行动项、周报
  11-milestone-acceptance/           # 阶段/最终验收、交付清单、确认
  12-closure-warranty/               # 收尾、质保、复盘、归档
  internal-finance/                 # 资源工时、费率、成本差旅、内部经营信息
  customer-deliverables/             # 本次明确选定的对客交付版本和清单
  archive/                          # 已替代版本及其来源/确认记录
```

原件快照只保留一份并由阶段材料引用，避免多处复制后版本不一致。代码、构建制品、模型等大型资产留在其专业仓库，项目包保存位置、版本、校验及访问/移交信息。

目录名称不是权限控制。第一版本地运行按授权访问；如共享文件夹，应使用真实访问权限或单独受限存储隔离费率、人员和合同敏感信息。客户包从交付白名单生成并审查内容，不能直接压缩整个项目根目录。密钥使用约定的安全渠道交接。

## 9. 复用模板与工具的实现建议

未来套件建议目录：`project-delivery-skills/skills/` 放 25 个兄弟技能；公共契约/模板规格位于共享资源，安装时按需要复制相关资源或提供明确的可发现入口，避免仅在源码仓库内可用的相对路径。

- 模板具有稳定 ID、版本、适用阶段、适用项目类型、字段定义、必填/条件字段和客户版规则。
- 文档/PPT 先生成有依据的内容包，再交现有工具渲染；客户模板可按字段映射适配。
- Master Plan、工时、预算、费用、风险、变更等优先可编辑表格；各对象只有一个主账，报告从主账生成。
- 确定性脚本只负责初始化、ID/版本登记、引用/金额/工时检查、汇总、交付清单等可复现操作；业务分析和材料判断由 Agent 完成。
- 初版本地项目索引保持单写者，多个 Agent 可独立产出草稿，再由总控登记；不把本地文件当多人并发数据库。
- 单项调用不强迫补齐整套流程。只生成周报时读取可用台账并标记覆盖；只做蓝图时说明缺失合同/调研依据，而非编造历史。

不在首版重复建设代码托管、任务平台、财务系统、音频转录引擎或 PPT 引擎；对接能力按实际环境和授权单独落实。

## 10. 分步建设与验证设计

### 第一批：先跑通真实项目管理闭环

优先实现交接、启动、调研/纪要、需求/蓝图、Master Plan、周报、里程碑确认的完整路径，并建立最小资源工时、预算差旅、风险/质量、变更台账。总控、来源和产物审核作为公共能力随主线建设。

用一个小型软件/集成项目，选一个有外部接口的业务模块，完整演示：合同义务 → 调研证据 → 蓝图/页面字段 → 工作包与实际交付版本 → 测试证据 → 客户确认包；运行至少一轮周会/周报，关联工时/费用和一次延期或变更分析。工程实施由现有开发能力完成或消费已有真实工程记录，不能用伪造测试/确认填补。

### 第二批：补齐软件实施深度与经营分析

完善 UI/字段/权限、接口联调、迁移、测试/UAT、上线回滚、培训运维移交；细化资源负荷、剩余工作、完工成本预测、外包和付款条件跟踪。

### 第三批：复用与系统对接

补充客户模板映射、不同计费模式/交付模式、质保收尾、多项目视图及飞书/任务/代码/财务等适配。是否建设平台由真实协作问题决定。

### 后续行为验收场景

| 场景 | 预期证据 |
|---|---|
| 合同缺附件，售前承诺与技术协议不一致 | 明确缺件与冲突、当前可推进范围、责任人；不生成伪确认 |
| 录音有模糊词、不同角色意见冲突 | 可定位来源、未知标记、澄清问题；决策不靠模型猜 |
| 蓝图到 UI/接口/UAT | 关键需求有页面字段/权限/接口及测试落点，排除项可解释 |
| 按模块确认实施蓝图，部分字段仍有争议 | 仅推进已确认/有明确先行授权的范围；未决项、版本与返工责任可定位 |
| 第三方接口延期 | 工作包/依赖/里程碑预测变化，纠偏选项及客户配合记录 |
| 蓝图确认后新增审批 | 候选与基线分离、成本/进度影响、实际授权后定向修订 |
| 已批准变更应用中途失败 | 各主账唯一责任、候选/有效集合分离；恢复后完整回读才生效，无半更新混用 |
| 同一出差申请→发生→报销→付款 | 只计一次发生，状态可追溯；未报销已发生不遗漏 |
| 采购承诺部分发生、漏填或未审核工时 | 承诺余额去重、暂估与实际分列、预测不因缺数据降为零 |
| 外包按小时暂估后收到结算单 | 以同一成本 ID 替换/冲销暂估，工时与结算不重复计成本 |
| 缺陷未复测/客户有条件确认 | 不冒充关闭/全部验收；保留影响、期限和责任 |
| 上线失败与回滚 | 记录实际动作/版本、恢复验证、未达成里程碑；不将计划标记成功 |
| 客户包混入费率/内部备注或旧版本 | 发现并阻止错误版本交付；实际文件内容/可读性复核 |
| 项目验收但质保未结束 | 验收、行政收尾、质保移交和质保结束状态各自正确 |
| 独立调用周报或蓝图、进程中断后继续 | 只消费有效输入，恢复真实状态；不补造阶段历史 |

验证分四类：结构/引用和计算检查；业务语义与跨文件一致性；真实 DOCX/XLSX/PPTX/PDF/原型打开或渲染回读；真实责任人/客户的确认与业务接受。自动检查通过只证明对应检查范围。
