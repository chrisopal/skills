# 商机评审闭环与成果依赖

## 已确认范围
先将原商机实现与12时间点案例合入main（1863bef6），再补两个P0闭环。不增加依赖、CRM服务或审批身份系统，保留同一SQLite主账、原子manage请求、幂等及revision检查。

## 决策与兼容
- 客户意见存入lifecycle.reviews：稳定ID、需求ID集合、被评审方案及摘要、责任人、期限、是否阻塞、意见、状态和审计历史。record_review / resolve_review / reopen_review保存来源；解决必须绑定当前方案与关闭证据。上游方案或文件变化后关闭记录保留，显示需复核。
- 成果的dependencies明确引用artifact_id与sha256，不依靠自由metadata。新报价依赖方案，谈判依赖报价，合同依赖报价及存在的谈判；直接采购允许没有谈判，不能补造阶段。登记时拒绝错误类型、过期/跨商机引用、摘要不符。复核以新成果版本重登记完成，不覆盖旧文件。
- 老数据可读、不补造依赖；缺少依赖的下游成果标记unbound/needs_review，不能作为新的推进依据。已签单历史保留，文件变更只改变核验状态，不能自动撤销签署事实。
- 阻塞性未关闭/需复核意见阻止报价、谈判、签约、赢单推进；方案整改阶段可以保留意见。事实/文件/签署记录各自独立。
- 拒绝独立评审服务与额外版本主账：现有生命周期JSON足够，避免重复真相源。

## 文件与执行
1. lifecycle.py、manage/lifecycle schema和运行层测试：实现评审对象与传递依赖核验，适配原测试/演练必要夹具。
2. renderer.py与模板：在真实商机详情展示意见、责任/截止日、关闭依据与复核原因；成果显示依据版本和有效性。
3. case_study.py：RV-01~03用实际manage写入/关闭；Q/N/C/H显式绑定依据；快照只读回真实状态。保留原12时间点评分/来源隔离。
4. Skill入口与共享契约：明确输入输出、操作和恢复/整改规则；更新版本、STATUS及验证记录。

## UI Blueprint
沿用enterprise-ui-design既有表格、语义色和亮暗主题。不新增装饰或无后端写按钮。客户评审表列：意见/需求、内容、负责人/期限、状态、方案/关闭依据；长ID/摘要放details。成果台账显示类型、版本、依据版本和核验状态。保留历史意见、文件下载、所有原导航及键盘语义。桌面1440和窄屏390、亮暗主题核验评审退回、关闭及合同页；无给定视觉参考，不宣称像素级对照合规。

## 验证
先保持既有52项测试，再加入真实重启回读、意见开闭/重开、错误证据原子回滚、错误依赖/上游替换传递失效、幂等/revision及旧数据兼容。完整CLI案例跑通至模拟签单；对一份隔离副本更换方案验证下游受阻。检查schema、链接、Python语法、差异空白与实际浏览器。生成数据库/HTML/截图保持本地。核验后Lore提交、推送并合入main；实际客户认可、签署真伪、回款和生产验收不属于此验证。
