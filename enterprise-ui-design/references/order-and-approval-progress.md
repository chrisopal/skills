# 订单、审批与服务单的阶段进度

这是[通用业务组件指南](business-component-patterns.md)中的一种模式，覆盖阶段连线、当前任务、并行执行和历史；不代表所有企业页面的默认布局。

## 1. 订单/委托状态：优先采用带连线的阶段条

### 横向还是纵向

| 情况 | 建议 | 不能用来掩盖的问题 |
|---|---|---|
| 桌面详情有足够宽度，阶段少、名称短 | 横向节点与连线，阶段名称在节点下方或右侧；下方独立显示当前任务 | 不能缩小字号、挤压节点或裁掉阶段名来保持横向 |
| 窄详情栏、390px屏幕、阶段描述长、需要责任与时间 | 纵向节点与连线，右侧排列名称、状态及必要说明 | 不能把桌面横条硬塞成横向滚动且隐藏当前阶段 |
| 阶段多，存在子阶段 | 按真实业务里程碑分组，当前阶段展开子任务 | 不能随意合并不同审批事实；保留查看全部阶段的入口 |
| 多个分支真正并行 | 总体里程碑概览＋分组任务列表；必要时用分支示意图 | 不把同时执行的样品/部门按顺序画成单条线 |

方向由**实际容器宽度和文案**决定，不能仅看屏幕宽度。可把“3–7 个短阶段”作为横向起点，随后用长名称与实际宽度验证；这不是硬性数量上限。纵向时当前任务摘要仍应靠前，避免完整阶段列表把关键操作推到底部。

示例（业务顺序须以宿主规则为准）：

```text
✓ 登记 ─── ✓ 受理 ─── ✓ 检测复核 ─── ● 报告审核 ─── ○ 交付归档
已完成      已完成       已完成          进行中          未开始

当前待办：综合报告技术审核
范围：样品 A、B · 跨两个检测场景        [查看报告并办理]
```

阶段概览中的“交付归档”若在宿主中是两个独立完成事实，应拆成两个节点或明确显示子状态；示例不能覆盖业务定义。

### 节点、连线和动作契约

- 节点同时使用图形和可读状态：已完成用勾；当前用强调轮廓/实心点加“进行中”；未来用中性轮廓加“未开始”；阻塞/退回用相应图形及文字；未知明确标注“待确认”。不能只靠颜色。
- 连线表达经过验证的顺序关系。已完成路径与尚未经过的路径有区分，通向当前阶段的线不能让人误以为当前也完成了。未知数据不能自动点亮此前所有节点。
- 阶段数据逐项来自业务事实；不能只凭 `activeIndex` 推断前面全部完成。退回、跳过、作废、并行和更正必须保留真实语义。
- 阶段概览是**进度指示**，默认不允许点击未来节点推进业务。只有真实导航能力存在时才做按钮/链接，名称说明去哪里；点击节点不等于完成该阶段。
- 顺序结构使用有序列表等语义；当前阶段可标 `aria-current="step"`，节点状态有文字，连接线是装饰、不进入焦点。若业务并行，不为满足组件 API 强制单一 current。
- “当前任务区”负责办理：业务名称、对象范围、必要前提、责任/等待原因、真实动作或查看入口。全流程只读时仍可展示阶段，但没有提交按钮是合理状态。
- 阶段总览与当前任务的状态来自同一事实集合。完成、失败或退回后应回读更新，不能一处停在旧阶段、另一处已经跳到新阶段。

## 2. 组合的留白与信息密度

用一个进度区域容纳阶段条，不为每个节点套卡片。节点间的线承担顺序关系，颜色/字重表达重点；位置、标签、状态有一致对齐。已完成历史可简略，当前步骤与异常可以有较多信息。

当前任务与阶段条邻近，业务明细放在后续区域。多条当前任务用列表；低频版本、哈希、内部 ID 放追溯入口。责任人、时间只显示有来源且影响判断的字段，不为填满组件补假数据。

水平重排为垂直时保留阶段顺序、状态文本和键盘顺序。对已完成全只读记录，可以优先显示结果摘要，再提供阶段和历史；进行中的只读记录优先当前等待状态。

## 3. 模式专项验收

| 检查 | 通过条件 |
|---|---|
| 顺序与范围 | 任一阶段的对象范围、状态和完成依据有来源；步骤条不把业务子项等同整单 |
| 当前定位 | 不读源码即可指出当前阶段、未完成事项和下一步/等待原因 |
| 连线语义 | 已完成与未完成路径可区分；切到阻塞、退回、未知时没有虚假完成连线 |
| 长内容与方向 | 桌面完整可读；窄容器切为纵向或合理分组；名称、状态、连线不重叠，不隐藏当前节点 |
| 交互语义 | 未来节点不伪装可推进；真实入口保留业务上下文；键盘可到达动作并正常返回 |
| 并行 | 两条执行线进度不同仍各自准确，必需项阻塞可见，跳过不冒充已执行 |
| 可访问性 | 文字说明状态，焦点可见，连线不抢焦点，浅/深和放大后仍能区分 |
| 回读与恢复 | 操作后总览与任务一致；失败保留上下文，未知不伪装完成，允许的重试真实有效 |

主线截图至少包含执行中、异常/退回、部分完成和完成只读；按产品适用性裁剪并说明。结合 [任务走查与构图规则](task-flow-and-hierarchy.md) 给出结论，不用“存在 Steps 组件”作为验收通过的依据。

## 4. 可运行订单阶段样板与 Blueprint

样板入口：[reference-order-flow/index.html](../assets/reference-order-flow/index.html)。在 Skill 根目录执行 `python3 -m http.server 8765 --bind 127.0.0.1`，打开 `/assets/reference-order-flow/`。它是明确标记的模拟数据，用于观察组件组合，不连接 LIMS、不办理真实订单。

Blueprint：

- 角色：办理人/只读查看者；目标：看懂订单进度和当前事项，查看对应样板明细后返回。
- 页面：一份订单详情；对象摘要 → 当前任务 → 连线阶段概览 → 样品/执行线明细 → 历史。桌面阶段概览可置于当前任务之前；窄屏优先当前任务。
- 阶段：登记、受理、检测复核、报告审核、交付、归档；各阶段显式记录状态。并行示例的检测执行线分开展示。
- 样例状态：报告待审、部分检测完成、退回补正、等待他人、读取失败、已归档。仅切换样例，不模拟真实签发成功。
- 布局：详情限宽到阅读 Token；页面/面板分别负责 inset，组内 8px、组间16px、区块24px，消费现有 Token。阶段组件按容器宽度决定方向；允许选择纵向展示以比较。
- 组件：原生 select/button/dialog/ol，复用本 Skill Token，不引入库。样板选择/主题/方向工具与业务动作分区并明确为演示工具。
- 交互：切换样例、浅/深、方向；当前动作打开带对应对象/范围的模拟明细；关闭恢复焦点；追溯可键盘展开。
- 证据边界：样板静态事实和浏览器交互只能证明模式；真实权限、后端状态和完整业务 E2E 必须在宿主实现后验证。


设计来源见[通用指南的官方依据](business-component-patterns.md#官方设计依据与适配边界)。

## 业务事件时间线：分组与追溯

- 独立时间线页保留明确的上级返回入口；页面标题表明对象与用途。按时间或业务场景切换只改变组织方式，不筛掉或复制原始事件，保持组内原有顺序；数据分页与来源失败提示继续可见。
- 按时间时以真实事件日期分组，按场景时以真实场景分组，并为无场景事件提供中性公共分组；组标题可显示当前已加载记录数，不冒称总数。
- 同组事件以统一列对齐时间、事件名称、人员、来源入口；窄容器按事件顺序转为单栏，长名称和标识自然换行。不要用分散的标签和大片空白代替分组。
- 两种视图的选中状态需同时具备可见样式与可访问状态；来源入口应保持真实可达。技术事件标识默认折叠但仍可键盘打开，未知操作保持中性，不推断事件含义。
- 验收实际数据与多日期、多场景、未知操作、无场景、长名称、空数据、分页、部分来源失败和只读权限；分别在浅色、深色、桌面与窄容器检查分组、事件一致性、对齐、焦点和溢出。
