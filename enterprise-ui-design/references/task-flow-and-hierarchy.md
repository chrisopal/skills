# 业务流程直观性与视觉层级

用于 Create / Upgrade / Audit 中的多阶段业务、委托/订单/审批详情、任务工作台、工具栏，以及“流程不直观、界面不好看”的反馈。它补充空间与 Token 规范；不规定所有产品采用同一流程或固定组件。

## 1. Blueprint 先表达业务任务

先读产品规则、真实接口和既有组件。画面顺序不能代替业务状态机。每条主线记录：

| 要素 | 设计必须回答的问题 |
|---|---|
| 角色与目标 | 谁在处理什么对象？本次要做成什么？ |
| 对象与范围 | 当前状态属于整单、子任务、样品还是某份报告？ |
| 阶段与依据 | 已完成、正在做、未开始、等待、退回、失败、跳过分别来自什么事实？ |
| 当前工作 | 哪件事需要关注？涉及哪些对象？有多个并行事项时如何分组？ |
| 下一步 | 当前人能执行什么？按钮去哪里、携带什么业务上下文？ |
| 阻塞与交接 | 缺什么条件、等待谁、谁可处理、如何恢复？来源未提供时标明未知，不编造责任人。 |
| 结束与证据 | 哪个业务事实才算结束？成功后查看什么结果，返回哪里？ |

主线应连贯覆盖入口、登记/编辑、校验或评审、执行、结果处理和结束；只纳入产品实际存在的阶段。每个阶段对应页面/区域、对象、操作权限、前置条件、可观察结果和返回路径。列出条件分支、并行汇合、退回、变更与只读路径，不凭想象补产品能力。

采用最适合任务的表达：

- **向导**：一次登记或配置中的有序输入；可返回修改，保留数据和校验定位。
- **阶段概览 + 当前任务**：跨角色、长时间运行的业务；阶段用于定位，任务区用于办理。
- **分组任务表 / 列表**：多个样品、场景、执行组同时进行；显示各自范围、状态和入口。
- **时间线**：回看已经发生的事实和责任，不能替代待办。
- **专业流程图**：确需查看分支依赖或配置逻辑时保留；不要让普通办理人先读引擎节点或 BPMN 才能完成任务。

可组合这些模式，不强制所有页面加步骤条、时间线、Tabs 或卡片。信息不足以支撑阶段聚合时，记录投影缺口；不能在前端猜测或伪造“完成”。

## 2. 详情的阅读顺序

默认顺序是 **对象身份 → 当前进展 → 待办/阻塞与动作 → 业务明细 → 历史与技术追溯**。已完成页面优先结果与证据；进行中的只读页面仍优先当前进展、等待原因和查看入口。

- 标题突出用户识别对象的业务编号/名称，邻近状态必须标明所属范围。长名称允许换行，不挤掉状态和动作。
- 当前任务使用业务名称；附近显示适用范围、必要责任信息和动作。不能让“待办理”与一段技术名称代替办理入口。
- 当前人无权办理时显示真实等待/权限原因，允许的查看入口仍可达；不强制出现主按钮，不展示绕过权限的假入口。
- 当前待办与必要阻塞默认可见。历史、哈希、内部 ID、旧修订和低频配置可以折叠；业务编号、决定当前操作的版本差异及关键警告不能一律藏起。
- 每条事实有主要展示位置。概览只汇总，明细负责展开，避免同一长名称、状态或版本反复占据首屏。
- 在选定的桌面和窄屏基准下，标题与当前进展/待办摘要应优先出现；明细可以滚动。不要以固定高度、裁切警告或缩小文字强行塞进首屏。

### 状态不能混用

- “已受理”是准入事实，“检测完成”是执行事实，“待报告审核”是当前任务，“已交付/已归档”是不同结束事实。适用于有这些业务概念的产品，不要求其它产品照搬。
- 子任务的 `2/2` 不代表整单完成；必须标注统计对象和分母依据，如“检测复核 2/2 项”。不把分支完成数直接变成订单百分比。
- 当前阶段用位置、文字和适当强调表达；成功色服务于明确完成的对象。若宿主约定中间阶段也用绿色，须让范围文字消除“整单结束”的歧义。
- 并行任务可有多个“进行中”；必需分支未完成时不把后续标为完成。跳过须来自真实条件决策，不等于执行成功。
- 读取失败或部分数据缺失显示“状态未能确认”及适用的重试入口；不能当作没有任务、全部完成或只剩一个阶段。
- “没有额外分支任务”只能描述分支配置；不能标题为“流程执行”却让读者误以为主业务没有工作。无关空分支可降为次要信息，真实缺项与错误仍需可见。

## 3. 工具栏：可识别不等于同等强调

先给动作分类，再选既有组件变体：

| 类别 | 常见内容 | 默认处理 |
|---|---|---|
| 当前业务动作 | 提交、受理、办理、审核 | 有实际可执行主任务时突出；多个同级并行任务用一致行操作，不把每行涂成主按钮 |
| 查询控制 | 筛选、添加条件、清除条件 | 靠近查询条件和作用范围，与结果连续 |
| 视图工具 | 列设置、刷新、导出清单 | 紧凑成组，降低相对权重；按频率决定直接显示或放入可访问菜单 |
| 危险/不可逆动作 | 删除、作废、签发 | 依业务语义和原确认规则呈现，不能为简洁与普通命令混淆 |

- 同组动作保持相同尺寸、字重和间距；页面标题与整组动作可两端对齐，不逐个拉散。
- 不为“必须有主按钮”而把刷新或列设置强行设成主操作。只读页面允许没有 primary。
- 降权用合理字重、底色、紧凑尺寸及分组；不得变成难辨认的灰色正文。若项目要求所有命令持续有边界，保留边界，通过其它维度区分。
- 控件尺寸按语义 Token 与实际 computed style 检查。截图像素可能受 DPR、缩放、裁剪影响，不能据此断言 CSS 高度不合规。
- 窄屏先保持作用域和组内关系再换行；“更多”适合低频项，但不能隐藏当前关键动作。纯图标动作须有可访问名称，不能只靠 hover 说明。

## 4. 审美判断落到可检查的构图

不是再加装饰，也不是只量像素。对完整画面逐项记录 `通过 / 不通过 / 未验证 / 不适用`，附证据；不以平均分抵消关键失败。

| 维度 | 通过所需的可观察表现 | 常见反例 |
|---|---|---|
| 视觉焦点 | 对象、当前进展与动作构成明确阅读起点 | 列设置/刷新比当前任务更醒目 |
| 层级 | 标题、阶段、条目、元信息可区分 | 全页加粗、多个同级大标题、标签墙 |
| 接近性 | 状态、范围和动作属于同一事项，组间边界清楚 | 状态在一处、操作远在另一处 |
| 节奏与对齐 | 与空间规范相符，留白帮助分组 | 反复分隔线、嵌套卡片、空白推开待办 |
| 信息经济性 | 名称与事实不无意义重复，技术追溯按需展开 | 多行内部编码占首屏，空流程独占大区块 |
| 长内容与重排 | 长名称、数值/单位、状态与按钮仍有关联 | 单位悬空、状态孤行、移动端只把所有内容堆叠 |
| 一致性与克制 | 复用宿主组件、Token 与语义色，边界清楚 | 局部补色/改字号，默认超链接样式与全站不协调 |

不能从一条截屏推断整个应用。没有认可的目标图时评估上述符合性，不给“还原度 95%”。审美意见应指出画面中的关系和用户影响，而非仅说“不高级”。

## 5. 验收：三类证据各自成立

### A. 业务状态与行为

从真实契约建立“状态/角色 → 显示范围 → 允许动作 → 结果/恢复”的矩阵。用宿主测试或隔离数据核验当前状态、权限、统计分母、导航上下文、返回后的选择/筛选，以及提交后回读；不以 CSS 或截图推断授权正确。

按产品适用性覆盖：待登记/待受理、执行中、并行部分完成、等待他人、退回/变更、读取失败、结果待审、完成只读。多个子对象至少包含不同进度，不能只用全部完成的单个样例。

### B. 无讲解的任务走查

让评审者从指定入口按界面寻找答案，不先告诉按钮位置或内部流程术语：

1. 当前在处理什么对象，范围是什么？
2. 走到哪里，哪些完成，哪些尚未完成？
3. 现在需要处理什么，当前人能做什么？
4. 若不能继续，缺什么/等谁，如何查看或恢复？
5. 操作后怎样知道成功，如何回到同一业务上下文？

记录每个答案依据的可见文字/区域、点击或键盘路径、误判和折返。若只能靠源码、内部 ID 或讲解回答，则不能通过直观性验收。截图只可支持其中可见的静态答案；缺少交互不能假定后续路径成功。

模型可以做启发式走查并明确身份；它不能代替目标用户测试或客户确认。不要编造“用户 5 秒看懂”或无真实测量的完成时长。

### C. 视觉与交互

在目标项目要求的视口、主题和密度下，逐张查看相同业务状态的截图，使用第 4 节评审表。测量实际字号/字重、控件高、组内/组间 gap、文字与容器对齐和溢出；检查键盘焦点、展开/折叠及返回。默认尺寸沿用 [checklist.md](checklist.md)，不额外扩大已明确的范围。

先跑宿主必要自动检查，再做任务/视觉评审。自动检查适合状态映射、链接上下文、权限呈现、溢出及回归；截图差异适合发现变化。它们都不能自动证明审美与流程可理解。未审过的截图不得直接写入“通过”基线。

### 判定

- **未就绪 / Not ready**：当前范围有未解决的 P0/P1，或约定范围内的主路径/关键角色缺少验证证据。前者记录已证实缺陷，后者逐项标“未验证”，不能混为发现缺陷；两者都不能声明可交付。
- **有条件 / Conditional**：约定范围的关键项已验证，仅有非阻断遗留或明确不在本次范围的缺口。列出限制，不扩大为完整流程通过。
- **通过 / Pass**：适用的状态、任务走查和视觉证据齐全，P0/P1 已关闭；明确证据来自模拟、真实系统、模型或用户。
- 没有主动作在只读/等待状态可以通过；缺少执行权限不等于设计失败。判定看状态是否准确、用户是否知道原因及可做的事。

使用 [评审模板](task-flow-review-template.md) 输出。仅有用户局部截图时，可确认局部问题并提出复查项，不能据此宣称整条业务流程验收完成。
