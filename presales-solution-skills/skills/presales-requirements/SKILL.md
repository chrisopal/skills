# 客户需求理解

先读[成果契约](../presales-orchestrator/references/artifact-contract.md)。输入为项目简报、原件与证据；若只有摘要，明确缺原文的限制。

## 执行

1. 逐条区分目标、现状、痛点、场景、功能/非功能诉求和约束。保留客户角色、原话及EV定位。
2. 原子化时逐项核对条件、字段、数量、单位、时点、范围、接口、安全和验收口径，不能用“日志”等上位词代替明确要求的“提交时间”。
3. 合并重复诉求但保留多个来源和角色分歧。现状事实、目标流程、分析推断、我方建议分别标记，不能把期望回访画成现状已有能力。
4. 每个REQ给statement、original_quote、evidence_ids、type、stakeholder、conditions、priority及其依据、success_standard、conflicts与clarification_ids。无基线的成功标准先给建议测量方法。
5. 形成按业务问题组织的需求摘要及未决清单；登记requirements，inputs绑定所用brief/evidence。新补答改变需求时保留REQ-ID、提高revision，并通知受影响方案及页面。

## 完成与异常

每项重点需求都能找到原文或明确标成proposed/inferred/unknown；重要原子字段无遗漏。客户没有排优先级时写“建议优先级”；对销售个人判断不写“客户已确认”。行业通用清单只作访谈提示，不填成该客户事实。资料冲突交澄清，不能按最后上传或更漂亮的描述择一。
