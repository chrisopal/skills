# 售前方案审核

先读[成果契约](../presales-orchestrator/references/artifact-contract.md)。先确定审核模式和输入范围，不能把只有PPT的审阅宣称为完整需求验收。

## 三种模式

- direction：需求摘要、脑图、候选方案。检查客户问题、主线、关键未知和方向依据。
- content：方案、大纲、内容包与原件。检查需求响应、原子字段、能力版本、范围、价值口径、逐页事实锁和制作充分性。
- delivery：当前内容包、真实PPTX/PDF、全部页面渲染及制作回执。先实际打开，再检查内容落地和文件可读性。

## 执行

1. 回读来源与当前hash。区分已见证据、作者陈述、推断和未核验项。条件允许时由未写该稿的Agent或人工审阅；没有独立条件就诚实标self-check。
2. 逐项对照需求 → 方案机制 → 内容页 → 实际页面。原子条件、字段、数量、单位、时点不能被泛化；现状与目标必须分开。
3. 检查主体、产品版本、标准/配置/定制/路线图、案例使用范围；未知接口不可写已接通，没有基线不可写收益比例，模板图片不可充当能力证据。
4. 检查核心问题是否贯穿方案与下一步；公司材料是否支持客户判断；跨页范围、阶段、术语及承诺是否一致。
5. delivery模式核验真实页数和顺序、全部文字与关键限定、图关系、备注、溢出遮挡、图源和编辑性。结构工具通过只证明其检查范围。必须查看真实输出渲染，不能只看源SVG。
6. 输出review envelope，inputs绑定目标；data写mode、target_id/target_sha256、verdict、实际method/reviewer、scope/unchecked和findings。delivery另绑定实际file_hashes。运行register及validate，不把命令输出当语义结论。

## 发现与复核

每项发现写FIND-ID、severity、对象/页码、来源依据、问题、影响、责任、动作、status与resolution_evidence。未经支持的关键承诺、错误客户事实、关键范围冲突、关键需求缺机制或不可读的关键页为blocking，阻止当前用途通过。其他问题分major/minor；不能用总分覆盖blocking。

事实不明回澄清、材料不足回选材、机制不成立回方案、表述缺失回写作、显示问题回PPT。读取整改后文件并重算hash再关闭；只给整改建议不是关闭。closed必须有实际resolution_evidence。

## 判定与完成

- pass：声明范围内无未解决影响使用的问题，并列未检查事项。
- conditional：限定使用范围、剩余问题、责任及条件；不自动进入正式PPT制作或外发。
- fail：存在阻止当前用途的问题。
- not_checked：缺证据或未执行。

产物是带版本依据的使用建议，不是客户确认或外发授权。客户输入不足时可审内部一致性与视觉，但“满足客户需求”保持未核验。最终报告必须列方法、覆盖、问题、复核证据、未检查事项与适用用途。
