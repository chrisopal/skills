## 原始材料独立执行

`field_validation.py prepare` 验证显式角色/来源/授权与脱敏说明，冻结原件哈希及摘录；生成没有业务答案的 Agent 任务。TXT/MD/CSV/JSON按逻辑行、DOCX按正文段落；未解析格式和失败内容列为未读，DOCX页眉/批注/嵌入附件须另补读取覆盖。

独立执行者读取8个实际 Skill，处理仓库自有虚构合同/技术草案/调研材料，登记11个产物，形成14条需求、业务蓝图、6个WBS/3个里程碑、独立实施设计和验收草稿。运行登记通过，13条精确引文通过来源/定位审核；主 Agent 另回读合同、需求、计划、验收及分析说明，核对范围外库存、验收角色、环境时间冲突、待定参数、缺失附件、财务与质保起算边界。结论为有条件讨论稿，0有效基线、0客户确认。

自动 `technical_pass` 仅检查哈希/引用/引文一致；`actual_material_validation` 只反映提交人声明来源为actual，不能当作真实业务验证通过。语义完整与真实客户接受分别审核。原件真实性不由此工具认证。

## 核心文件

`export_core_documents.py` 读取通用运行项目当前候选，拒绝损坏/过期核心记录及覆盖已有输出，另保留批准有效集合。六套原生DOCX/MD为启动会、业务蓝图、详细设计、WBS、接口迁移、里程碑验收；按模块保留页面/字段/权限/接口等内容，拆分过宽表和嵌套操作，补全验收遗留项、WBS精确完成证据与人员。未知数据不填造。

最终6套文件均实际渲染：3/5/8/4/3/7页，共30页。逐页检查表头、换页、边界及可读性；未改内容与上一渲染的MD及DOCX所有解包成员逐项相同，变更的启动/WBS/蓝图/接口重看全部页面。保留完整来源哈希清单。目录混有内部设计/计划/接口和清单，不能整体对客发送；客户草稿的自由文本仍需独立敏感信息与业务审核。
