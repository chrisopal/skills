# Prototype

Use prototype work to answer product and workflow questions before or during implementation.

## Prototype Choice

- Flow prototype: best for business process, approval, or state transitions.
- Static HTML prototype: best for quick layout and interaction review without app integration.
- Existing frontend route: best when design must match an existing product.
- Clickable/data prototype: best when workflow logic or realistic records matter.

## Prototype Brief

Capture:

- Purpose
- Target users
- Scenarios covered
- Requirements covered
- Screens or states
- Data assumptions
- Interaction notes
- Validation questions
- Known gaps

## Build Rules

- Reuse the existing frontend stack and design system when inside an app repo.
- Do not create marketing landing pages unless the user asks for one.
- Make primary workflows usable on the first screen.
- Verify with a browser or screenshot when the prototype is visual and runnable.
- Keep prototype gaps explicit so they do not become accidental requirements.
