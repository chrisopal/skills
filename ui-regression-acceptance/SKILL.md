# 界面回归验收

目标：发现“接口和单元测试都绿，但用户实际操作失败”的问题。每个范围内的控件实例都要有验收记录；有限的适用状态清单可以全部执行，不能声称穷尽所有输入和状态组合。

## 进入验收

从现有上下文确定 URL、工作树/构建版本、页面范围、角色、测试数据及已有浏览器工具。用户要求“整个应用”时，盘点全部可访问业务路由、弹窗、抽屉和动态子页面，分批完成；不能自行改成首页或几个代表性页面。不要为常规选择重新提问，只有缺失的环境、账号或范围会实质阻断时才问。

默认执行验收、生成复跑测试和报告；修复产品代码需属于用户已有授权（例如“验收并修复”）。复用已有测试账号/受控凭据，凭据只保留在内存或已有受控认证状态，不写入测试、截图、日志。通常以隔离环境和合成数据执行可逆写操作；已有授权持续有效。真实外发、支付、生产删除等不能因“全量点击”而自动获得授权，缺少授权记 BLOCKED 并继续独立用例。

使用现有浏览器 MCP、Playwright 或等效真实浏览器能力，按工具契约操作，不安装第二套框架。使用已有框架时按仓库规范扩展测试；没有框架时保留实际可复跑脚本与运行前提。没有浏览器能力时，只能交付盘点/测试计划，执行状态为 NOT_RUN。

## 1. 契约匹配与四维台账

先阅读 [业务契约矩阵](references/business-contract-matrix.md)，把业务/接口、交互状态、字段显示、视觉布局四个维度落实为逐控件检查。包括页面整体的对齐、字体、宽度、间距和条件布局，不能只测控件能否点击。字段的类型、长度、精度、显隐和动作权限来自需求与后端契约；禁止把当前页面或服务端表现直接当成正确标准。来源缺失/冲突时标 BLOCKED。



结合路由/组件源码和真实 DOM/可访问树盘点，互相补漏：隐藏菜单、条件字段、不同角色入口、标签页内部、弹窗及浮层。不要把 DOM 自动扫描当作完整清单。

开测前阅读 [范围盘点与用例设计](references/inventory-and-cases.md)，先从源码和契约形成独立 `scope.json`，再用真实界面校对；它与执行结果 `coverage.json` 分开保存，并绑定摘要。逐页标明源码位置、入口/参数、角色与状态、控件实例和四维检查。无路由的弹窗/抽屉也作为独立页面上下文；每页必须有 `kind=page` 的整体布局实例。无法进入的页面仍保留，标阻断或未测，不能从分母消失。

台账以“页面 + 控件实例 + 行为链”为单位：稳定 ID、业务名称、角色/前置数据、可访问定位、适用状态、预期结果。同一种下拉框在不同表单中仍是不同实例；表格重复行可按行为等价分组，记录分组及代表数据，不必盲点每一条记录。没有可靠定位时记录可访问性缺口，并使用稳定替代定位。

阅读 [控件验收矩阵](references/control-matrix.md)，为实际存在的控件分配适用检查。先冻结台账；发现新控件要追加记录，不能为了提高覆盖率删除失败/未测条目。跨组件复用测试不能替代每个页面的集成检查。按关键写流程 → 其他控件实例 → 异常和布局组合执行，整个应用验收必须继续覆盖后续批次。

详情分组、业务流程、只读资料、列表工具栏或冗余提示在范围内时，应用 [信息结构与工具栏检查](references/information-hierarchy-and-toolbars.md)。把语义分组、结构化只读字段、长叙述独占整行、局部空态居中与状态分类、操作主次及提示必要性纳入设计、开发和最终验收；逐个页面实例核对，不以无溢出或组件测试代替。详情按其中 DETAIL-01～04 逐项验证页头状态邻近、字段组限宽、校验码命名/展开及摘录层级；内容→决策区另用 SPACE-09 验证唯一间距 owner，不能因用了 dl/grid 或按钮组 gap 就通过。

涉及缺陷复测、名称/标识、配置表单、动作资格、筛选导出或详情导航时，按 [飞书缺陷回归断言](references/feishu-lessons.md) 选择适用 UAT-F 检查，展开到页面/控件实例。保留人工否、新反馈和原失败证据；L1 静态/台账检查不能证明业务语义或替代真实浏览器验收。

涉及指标首页、宽表详情、行高/排序、统计编辑与预览、权限分组或图表/表格切换时，按 [运营工作台布局检查](references/operational-layout-checks.md) 展开适用 UAT-O 断言；通用只读表或已有主列表还要展开其中的 [通用表列布局检查](references/operational-layout-checks.md#通用表列布局检查)，覆盖 `TABLE-L01`～`TABLE-L09`；涉及折线、柱/条、饼/环、堆叠、直方图、散点或统计口径时，再按 [统计视图真实浏览器检查](references/statistical-view-checks.md) 展开 STAT-U01～U12。实际执行导航、排序、完整值读取、搜索与视图切换，核对真实布局和数据；不以固定列数、记录数、填满页面或 CSS 声明替代验收。

所有视觉走查必须应用 [组件留白与间距均衡检查](references/component-spacing.md)：独立组件之间须有可辨认留白，同层同类间距均衡，容器边界到控件也须留白。按钮贴分隔线、字段组粘连等即使没有重叠或溢出，仍判 FAIL；不能只检查 CSS 声明了 gap。逐页面、子页、Tab、弹窗及条件区域记录实际间距、Token 来源和截图；有意拼接的组件须记录例外依据。

每个维度分配独立检查 ID，填写该维度的具体断言；同一次操作/截图可以支持多个检查。N/A 的检查和理由在范围清单中预先声明，执行时不能把失败或困难用例改成 N/A。发现新增项或适用性变化，保留原清单与结果，修订范围后补跑受影响项。

## 2. 每项验收都走完整状态转换

基本链：进入页面 → 定位真实控件 → 操作 → 等待实际状态/响应 → 点击其他位置或 Tab 失焦 → 检查显示与值 → 再次打开/修改 → 提交（适用时）→ 刷新或重新进入 → 回显/持久化检查。

- 下拉必须选择非首项，再切换另一项、失焦、重新展开，核对选中项及显示文字；可清空、过滤、远程加载、联动时分别验证。读取 input.value 不能代表自绘下拉选中值。
- DOM 中有文字不等于用户看得见。失焦前后检查控件和标签的 bounding box、可见区域、颜色、遮挡、截断；对可疑布局状态截图并实际查看。不要以全局固定宽度阈值判断所有控件正常，断言应来自该控件设计和可读性需求。
- 按用户操作点击，不用 force click、直接改 v-model/localStorage 或 DOM 值绕过控件。page.evaluate 可用于只读测量/断言；API 可准备合成数据、回读，但不能替代被验收的 UI 动作。
- 等待网络完成、选项渲染、浮层进入/退出或业务状态；避免固定 sleep 和 selector.nth 猜测。浮层应定位当前可见且属于当前控件的列表，避免点到正在退出的旧列表。
- 区分“按设计在重进后重置的临时筛选”与“应保存的业务值”；只对有持久化契约的值要求刷新保持。弹窗关闭/取消同样按契约判断，不武断要求清空或保留。
- 写操作必须核对实际请求的字段和稳定标识、服务端结果及独立 GET/详情回读。成功 toast、HTTP 200 或假响应单独都不算端到端通过。脱敏记录，不导出完整认证头/隐私数据。
- 检查二次打开、取消再开、切换工作区/角色、返回页面后的旧值、错误和忙碌状态。只读/禁用动作不能产生写请求。

脚本先用一个代表控件验证定位与交互策略，再批量展开。组件库常把原生 input 隐藏在可见标签下：操作可见标签或真实键盘焦点，不能把隐藏 input 的点击超时直接认定为产品缺陷。缩放、步进等先核对是否已到边界；每个独立用例明确前置状态和恢复步骤。

抽屉/弹窗关闭除了检查隐藏，还要检查 `document.activeElement`：普通关闭按契约返回入口或合理的可见控件；跳转关闭则进入目标区域，不能停留在隐藏内容。不要将非模态面板强行套用模态焦点锁定规则。

## 3. 环境和视觉组合

每个控件实例在主业务环境执行基本链。再按差异风险安排组合：用户实际出现问题的浏览器/嵌入容器、受支持窄屏/桌面断点、实际主题开关、长中文/英文、长选项、空值/零值/合法边界、空/错误/加载状态和键盘操作。

不要求所有状态做笛卡尔积，也不允许未经说明省略范围。共享组件已覆盖组合可以引用证据，但页面局部 CSS、容器宽度、Teleport、权限或绑定逻辑不同的地方必须独立测。浏览器模拟失败/慢响应验证的是前端恢复路径，标为 SIMULATED，不能混作真实端到端成功。

浏览器不同导致无法复现时，报告准确环境差异，保持原问题 UNCONFIRMED，不用另一个浏览器通过宣布用户问题已解决。

截图在相关滚动、布局和过渡稳定后采集；缩放/拖拽前重新读取容器坐标。存在短暂交互抑制时，等待可观察的就绪条件并保留依据，不靠任意延长 sleep 掩盖问题。动画中间帧只能作过程证据，不能单独证明稳定布局缺陷。

## 4. 失败闭环与复跑

失败立即保存最小复现：控件 ID、环境、步骤、预期/实际、截图和脱敏请求证据。失败项标 FAIL；依赖它的后续项标 BLOCKED，继续其他独立控件。不要因为发现一个问题就终止整套验收。

先区分产品断言失败、脚本/定位错误和前置状态污染。脚本失败不得直接算产品缺陷，也不得覆盖为 PASS 而丢弃原记录；纠正后用同一业务断言复跑并注明归因。前序失败导致筛选/弹窗未恢复时，恢复并验证基线后才运行后续独立用例，否则记 BLOCKED。不要把一串继发失败报成多项产品缺陷。

在已授权修复的范围内：先保留能复现该失败的浏览器回归用例 → 最小修复 → 原步骤复测 → 同组件其他实例和直接相关流程回归。布局问题应保留真实浏览器几何/可见性检查，不能用无布局的 DOM 单测宣称已防回归。未经授权修复时交付问题单和复跑脚本，不擅自扩大修改范围。

## 5. 交付与判定

在仓库约定目录，或 `output/ui-acceptance/<run>/` 保存：
- 独立冻结的 `scope.json`：源码/运行界面盘点证据、页面/控件/检查项、预期版本与 N/A 理由。
- 页面/控件台账与逐项结果 `coverage.json`，格式见 [证据格式](references/evidence.md)。
- 实际执行的浏览器脚本/用例及准确复跑命令，必要的脱敏截图、测量和回读。
- 报告：环境/版本、范围、通过/失败/阻断/未测/不适用数量，问题严重程度，修复与复测，剩余缺口。

运行 `python3 <本技能目录>/scripts/check_coverage.py <run>/coverage.json --scope <run>/scope.json`，核对范围、版本、四维分配、适用性、复跑文件和证据完整性。执行覆盖率的分母来自独立范围；逐页/逐控件分别列出完成、失败和未完成数量，混合状态的实例按最差结果归类。该脚本只能审计记录，不能证明盘点已穷尽、真的点过、截图正确或业务正确。必须查看实际脚本、日志、截图/测量和回读，核对每个 PASS 的断言与证据；报告分开写“台账校验结果”与“浏览器业务验收结论”。

PASS 仅表示已声明范围的全部适用检查通过，且无阻断/未测/未确认。FAIL 表示仍有失败；INCOMPLETE 表示有未测/阻断/未确认。N/A 必须写具体理由，不计入执行覆盖率。小计与总数都报告，不能把“已执行测试全绿”写成“整个界面验收通过”。

当前构建/类型检查/API 测试与本次浏览器验收分开报告。最后说明执行范围与真实剩余限制，不承诺下次 AI 会自动穷尽所有 UI 问题。

## 6. 版本与门禁衔接

使用 references/evidence.md 的 schemaVersion 3 台账与 schemaVersion 1 范围清单。开测前冻结范围和源代码/构建标识，记录预期运行版本；开始与结束时观察服务中的实际版本并保留证据，中途变化则分开新一轮验收。来源指纹仅能识别源代码变化，不能证明服务器部署了该版本。旧 v2 及其他旧格式台账不得作为新门禁 PASS，补齐范围、复跑与实际版本证据后重新核验，不自动迁移为成功。

PASS/FAIL 的证据限制在本轮目录内，记录 SHA-256；拒绝绝对路径、目录穿越和越界符号链接。修复后保留原失败证据到 previousFailures，最终结果关联复测；不得覆盖或删除原失败记录。

项目接入时固定技能/检查器版本到仓库，CI 不依赖某台机器的 ~/.codex 路径。用独立的范围清单核对页面/控件/检查项，再匹配版本和审计台账。缺少运行应用时记录 NOT_RUN/NOT_APPLICABLE 的前提状态，不能产出业务 UI PASS；已有应用而缺环境或证据必须阻断验收。脚本只审计记录，不自动操作浏览器，不证明证据语义真实。
