# 公众号文章审核清单

## Topic Pool Integrity

- 是否有稳定的 `topic_id`，并能在本地选题池和 Get笔记主索引中定位到同一条记录。
- 是否完成近似标题、案例名和核心问题的重复检查。
- 本地开始写作后是否标为 `DRAFTING`，本地成稿后是否标为 `READY_LOCAL`。
- 是否只有在取得 `media_id` 且完成 `draft/get` 回读后才标为 `DRAFT_SAVED`。
- 是否只有在用户确认或公众号后台/公开链接证明发布后才标为 `PUBLISHED`。
- 状态改变后是否更新本地主索引，并同步更新 Get笔记中的同一篇主索引笔记。

## Positioning

- 是否围绕“把 AI 技术讲明白 / 把企业真实发生讲清楚”。
- 是否避免狭义地只围绕 Agent 工具拆解。
- 是否服务 AI 应用开发者、技术管理者、企业数字化负责人。

## Content

- 开头是否 150 字内说明为什么读者应该读。
- 技术概念是否解释了：解决什么、怎么工作、适合谁、不适合谁。
- 企业落地是否解释了：进入哪个流程、谁使用、谁维护、风险和收益。
- 是否有案例、场景、失败复盘或可操作判断。
- 如果是主文，是否尽量锚定了真实公司、真实产品、真实流程或真实改造路径。
- 是否讲清了：怎么落地、用了什么技术、拿到了什么价值。
- 是否避免只写概念、口号、新闻摘要。
- 是否明确属于案例复盘、阶段总结、失败复盘、客户决策或方法文中的一种，而不是把所有文章都写成搭建教程。
- 案例文是否用真实证据开篇，并让案例贯穿全文，而不是开头提一下、后面重新变成通用框架。
- 总结文是否说明观察范围、给出反例，并落到客户下一步怎么判断。
- 是否让潜在客户看见一个具体的预算、使用、验收、ROI 或供应商选择问题。
- 非虚构长文动笔前是否至少有五件具体、可追溯的材料；不足时是否先研究、缩题或缩短，而不是重复解释凑字数。
- 现实案例、第一人称动作、引语和精确细节是否有来源，是否避免模型临时编造“典型工厂现场”。
- 每个正文段落是否新增事实、动作、例子、区别、限制、后果或有依据的判断。
- 删除三分之一后若事实和结论几乎不变，是否保留了压缩后的版本。

## Style

- 语气是否像人在讲话，有对象感。
- 是否保留作者判断，而不是泛泛正确。
- 是否有明显 AI 味：过于顺滑、过于平均、过于像总结稿。
- 是否避免套话和高频模板句反复出现。
- 是否避免把全文推进建立在少数几个口头禅上，例如 `真正值钱的`、`最值得企业学的`、`下一步该补的`、`不是……而是……`。
- 是否避免“评论腔”判断句，例如 `这条线很值得盯`、`更值得关注的是`、`这个信号是`、`下一步该补的是`。
- 是否把长判断句改成了更短、更像人说话的中文，而不是一串抽象总结。
- 是否至少有几段能明确点出角色、动作、对象，而不是只反复说“企业”“团队”“系统”。
- 是否像一篇成熟的商业解释型专栏，而不是咨询报告、行业快评或 AI 总结稿。
- 是否做到“结构是商业解释型专栏，但表达仍然自然，像人平时真的会这样说话”。
- 是否做到“小节只回答一个问题”，并在段尾留下一个可复述的判断。
- 是否讲得像“一个人对一个具体读者说话”，而不是对所有人广播。
- 是否和最近几篇文章相比没有明显重复同一种开头、过渡和结尾手法。
- 最近四篇主文只要出现过“怎么从 0 到 1 配一个……”，本篇是否避免继续复用同一标题和七步结构。
- 是否没有夸张标题党。
- 是否没有过多缩写堆叠。
- 是否按修辞动作识别“先制造读者误解、再推翻抬价”的翻案腔，而不只搜索 `不是……而是……` 字面。
- 真实的观点修正是否写清原判断依据和改变判断的具体材料，而不是套 `你以为 / 其实 / 才发现` 句式。
- 是否避免三项以上同构排比、连续同长度句子、短段排队和固定段落开场。
- 是否删掉多余的 `因为 / 所以 / 但是 / 同时 / 此外`，让对象、动作和因果承担连接。
- 是否把 `进行了优化 / 实现了提升` 改成具体角色、动作、对象和可见结果。
- 是否运行 `scripts/check_human_tone.py` 辅助发现模板形状，并由审稿人结合上下文作最终判断。

## Layout

- 是否使用统一风格系统。
- 是否没有原生 `<ul>` / `<li>`。
- 是否有封面图；深度文应尽量有 1 张正文插图。
- 如果是案例深度文，是否考虑 2-4 张图：痛点链路、方案架构、工作台/界面、价值闭环。
- 封面和插图是否已经保存到仓库内真实路径，而不是只停留在 `imagegen` 缓存或会话预览。
- 如果仓库定义了配图持久化记录文件（例如 `assets/wechat/imagegen-manifest.jsonl`），是否已经留下本次图片的记录。
- 图片命名是否稳定清楚，能从路径直接看出文章 slug 和图型。
- 标题、摘要、正文、页脚是否完整。

## Image-Post Visual Review

用于 `工业AI日报` 的单篇多图 `newspic` 草稿。每张 9:16 fullcard 进草稿前都要过一遍，不通过就重画。

- 是否包含 `公司/地区`、`整体方案`、`图例链路`、`做了什么`、`方案抓手`、`业务价值`、`我的判断`。
- `整体方案` 是否讲清端到端做法，而不是一句短标签或泛泛描述。
- 版式是否像工程笔记：白底纸面感、细线分区、编号、墨绿/深灰/少量橙色。
- 标题是否没有挤占正文空间；正文是否有足够案例说明。
- 图例链路是否能看懂工业流程或系统路径，不只是抽象图标排队。
- 中文是否清晰可读，没有溢出、重叠、断字、错字、乱码。
- 是否没有真实公司 logo、水印、人物、装饰性工厂插画、假仪表盘或复杂背景。
- review markdown 是否记录每张图的审核结论、需改点、最终图路径。

## Publication Boundary

- 只允许保存草稿。
- 不允许调用发布接口。
- 输出必须包含待审核信息：标题、摘要、封面路径、草稿 media_id、审稿结论、建议调整点。

## Rewrite Loop

- 如果人工反馈明确指出“AI 味重”“读起来拗口”“像套模板”，不要只做局部换词；优先重写开头和高频判断段。
- 如果文章从一个虚构的工厂角色开场，再顺滑进入资料包、工作流、权限和验证步骤，应按结构性模板问题退回重写。
- 如果当天草稿已经保存，文风修改优先 `update-draft` 覆盖原 `media_id`，不要堆叠新草稿。
